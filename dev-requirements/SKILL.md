# dev-requirements：需求

目标：**把要做的东西一次问清、写死，让后面的阶段不用再回来问人。**
这是用户必须参与的阶段：定方向只有用户能做。但最多打扰两次：需求评审消息（有必要时）和关口 A。

## 开始

1. 先读 `../dev-workflow/SKILL.md` 的“每次开始时”，照做其中第 1–3 步（包括读 `../dev-workflow/references/decisions.md`）。本阶段还要读同目录下的 `questions.md`、`layout.md`、`preview.md`、`gates.md`。
2. **接着做**：已有需求文件夹、状态行“阶段”是 `dev-requirements` 时，看 spec 写到哪了，从对应的步骤继续，不要重建文件夹、不要重发已经回答过的评审消息。

## 1. 定规模，建文件夹

1. 先判断规模（微小 / 小 / 标准，见 dev-workflow）。**是在修 bug 时**（包括微小的），先用 `git log` / `git blame` 查是哪个 devflow 需求引入的，查到就按 metrics.md 在那个需求里记一行“合并后发现问题”。**微小**：不走本流程，直接改、跑测试、在回复里说明，结束。
2. 从默认分支新开本地分支：`git switch -c change/<短名> <默认分支>`（不管当前在哪个分支；一批需求时每个需求都这样开，做下一个之前先切回默认分支）。当前有未提交的改动时，用 `git stash push -u -m "devflow: <短名> 之前的改动"` 收起来，并在第一次汇总里告诉用户（**不要**替用户提交这些改动）。离开模式、一批需求（L3）、或用户还在这个仓库里干别的时，改为在仓库外建 worktree（`../dev-workflow/references/away.md`），不切换用户当前的目录，也就不用收起他的改动。
3. 按 layout.md 建 `<docs_dir>/<日期>-<短名>/`，按 [references/spec-template.md](references/spec-template.md) 写 spec 骨架，状态行：`状态：草案　阶段：dev-requirements　待关口：—　等级：<自主等级>　规模：<小/标准>`；建 `decisions.md`（文件头见 layout.md）和 `metrics.md`（见 `../dev-workflow/references/metrics.md`，第一行记“阶段开始”）；在索引里加一行。
4. **一批需求（L3，或用户一次给了几个互相独立的需求）**：先在默认分支的索引 `<docs_dir>/README.md` 里登记这一批（每个需求一行，按处理顺序，状态“草案”），提交这一次只改索引的更新；然后每个需求各开分支、各建文件夹，按下面的步骤逐个做到第 7 步，最后合成**一份**关口 A。各分支只改索引里自己那一行，合并有冲突时以默认分支的为准再改自己那行。

## 2. 先查

读用户提到的文件、相关代码、已有的需求文档、`git log`，以及 `.devflow.yml` 的 context，直到能说清：**现在是怎么工作的，这次要改动哪些部分，哪些已有的东西能复用**。

## 3. 需求评审：确认做的是对的东西

按 [references/product-review.md](references/product-review.md)（借鉴 gstack）做，结论先写进 spec 草稿：
1. 判断需求类型，决定追问的严格程度；
2. **前提挑战**：问题找对了吗？什么都不做会怎样？现有代码解决了多少？交付物怎么到用户手里？写成 2–4 条前提 `P<n>`；
3. 说法含糊时，直接改写成你的理解，而不是反问；能用运行结果回答的疑问（某个做法行不行、快不快、显示效果），先做一次性原型跑一下（decisions.md 第一节），不进问题清单；
4. 有明显不同的做法时，列出产品层面的 2–3 个方案（必须有一个“最小可行”），写明推荐；
5. 按规则推荐范围模式（扩展 / 选择性扩展 / 保持 / 缩减），列出扩展候选 `E<n>` 或推迟候选；
6. 标准规模做一次理想状态对照：现状 → 本次 → 一年后。

然后按 [references/gap-checklist.md](references/gap-checklist.md) 逐类扫一遍缺口，每类标“清楚 / 部分 / 缺失”。“部分”和“缺失”的每一项：
- 有合理默认值（行业惯例、项目惯例、能从需求推出来）→ 自己定，写进 spec 的“假设”（`H<n>`），写明依据；
- 没有合理默认值，而且答案会改变要做的东西或验收方式 → 放进待问清单（`Q<n>`）。

待问清单按“影响 × 不确定性”排序，标准规模最多 5 题，小规模最多 3 题，多出来的按推荐定、写进假设。

## 4. 发一条评审消息

按 product-review.md 第 7 节的结构，把理解、前提、做法、范围、问题合成**一条消息**发出，每一项都带推荐，人回 `all` 就能全部按推荐。状态行写 `待关口：评审`，提交 spec 草稿，**这一轮结束，等人回答**。

可以不发、直接往下做的情况：理解没有歧义、前提都是从代码里查实的、只有一种合理做法、范围模式是“保持”、也没有高影响问题。这时把前提、假设和中低影响的问题都放到关口 A 一起确认。

收到回答后（按 gates.md 的解析规则，`all` 即全部按推荐）：清空“待关口”；答案写进“问答记录”和正文；扩展候选按人的选择写进“范围”“推迟到以后”或“不做”；不同意的前提重新梳理，影响大时最多再发一轮，只问受影响的部分（decisions.md 的例外 2）。

## 5. 写 spec

按 [references/spec-template.md](references/spec-template.md) 写完整：
- **需求写成“系统必须……”**：一条只说一个行为，外部能观察到；“好用”“快”这类词必须量化或删掉。
- **每条需求至少一个场景**：假如 / 当 / 那么，要能直接变成测试。要覆盖出错、空数据、无权限、重复操作这些容易出问题的情况，不只写正常流程。
- **只写行为，不写实现**：类名、库、表结构放到 design.md。
- **写明完成条件**：一句可检验的话，说清怎样算做完（例如“12 个场景在浏览器里全部通过，旧接口没有调用方”），机器关口 C 按它判断。
- 规则里有 `rules.requirements` 的，逐条满足。

自查：每条需求都有场景；场景能测；“不做”写清楚了；没有“待定”“TBD”。

## 6. 新人通读检查（标准规模）

派一个子 agent，用 [references/builder-check-prompt.md](references/builder-check-prompt.md) 让它读 spec。它提的问题分三类处理：
- 文档里其实有答案 → 把那部分写清楚。
- 小事，合理的开发者自己就能定 → 自己定，写进“假设”。
- 只有人能回答、且会改变要做的东西 → 带默认值，作为 `Q<n>` 放到关口 A。

没有子 agent 工具时，自己扮演没看过对话的开发者通读一遍。

## 7. 效果页

需求涉及界面、交互、或多步流程时，按 preview.md 生成效果页并上传：
- 覆盖每个关键场景的样子（正常、空、出错、无权限）；
- 项目已有界面的，模仿现有样式；
- **有口味类的选择、而且选错了返工很大**（布局、风格、交互方式看了才知道喜不喜欢）时，不要只做一版：按 decisions.md 第一节第 2 条做 2–4 个真正不同的方案，放进同一个多方案对比页（preview.md），推荐其中一个，在关口 A 请用户回 `M<n>` 一次选定；
- 链接写进 spec 的“效果页”一节（访问码不写进文件）。

纯后端、命令行、库的需求，用一张示意（接口示例、命令输出示例、流程图）代替；实在没有可看的，就跳过。

提交 spec、效果页源文件和 `.dview.json`。

## 8. 关口 A

**规模“小”**：先在需求文件夹按 `../dev-design/references/tasks-template.md` 写 `tasks.md`：开头 5–10 行技术方案（改哪里、怎么改、为什么），然后测试计划和任务。小规模不经过设计阶段，这些内容随关口 A 一起确认。

按 gates.md 的“关口 A”格式给出简报（小规模加上技术方案和任务数；一批需求时每个需求一节，回复对整批生效，单独改某个需求时写需求短名，如 `comments：Q3 B`）。每个 spec 状态行写 `待关口：A`，提交，**这一轮结束，等用户回复**。

回复按 gates.md 处理。通过后，对每个需求：清空待关口，写变更记录，提交，更新索引；然后——
- **标准规模**：状态改为“已确认”，阶段改为 `dev-design`，读 `../dev-design/SKILL.md` 并执行；
- **小规模**：状态改为“开发中”，阶段改为 `dev-build`，读 `../dev-build/SKILL.md` 并执行。

一批需求时，逐个往下做完一个再做下一个（每个需求在自己的分支上），汇总按需求分别更新。

## 不要做的事

- 不要把能从代码里查到的东西拿来问人。
- 不要一题一题地问；不要问实现方法。
- 不要只做“记录员”：人的说法有问题、有更简单的做法时，要在评审消息里直说。
- 不要悄悄扩大范围：扩展只能由人在评审消息或关口 A 里选择加入。
- 不要把没确认的事写成确定的：AI 定的都放在“假设”里。
- 不要在关口 A 通过之前写产品代码；效果页和一次性原型不算产品代码。
