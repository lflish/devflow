# dev-accept：验收

目标：**让人在几分钟内判断“做的是不是我要的”，并把所有攒下的决定一次处理完。**

## 开始

1. 先读 `../dev-workflow/SKILL.md` 的“每次开始时”并照做（包括读 `../dev-workflow/references/decisions.md`）。本阶段还要读同目录下的 `gates.md`、`preview.md`。
2. 找不到需求文件夹时，本 skill 不适用：告诉用户这是需求流程的验收步骤，问题不大的话改用 dev-review 的独立模式。
3. 状态改为“待验收”，阶段改为 `dev-accept`，同步索引。

**接着做**：验收页已生成、只差简报的，直接到第 4 步。

## 1. 收集

spec.md、design.md、tasks.md、decisions.md、test-report.md、review.md、`evidence/` 下的截图、git 记录（`git log <基准>..HEAD`）。

## 2. 核对

| 方面 | 检查 |
|------|------|
| **完整** | 任务都是“完成”（“阻塞”的单独列出）；每条需求都有对应代码；每个场景都有测试且有结果；后续清单里没有本该在这次完成的东西 |
| **正确** | 场景全部通过；挑 2–3 个最重要的场景，用测试浏览器亲自走一遍，和截图对得上；spec 里的具体数值、文案、权限在代码里一致 |
| **一致** | 设计里的决定在代码里都能看到；实现中的偏差都记在 design.md 的“变更”和 decisions.md 里 |
| **干净** | 没有未提交的改动；没有调试代码、临时文件（`.devflow-tmp/` 不在仓库里）、注释掉的大段代码；全部测试和 lint 通过（重新运行一次，附输出） |

问题分三级：
- **严重**：场景没实现或结果不对、测试失败、数据风险、阻塞的任务。能修的：在 tasks.md 加“返工”任务，状态改回“实现中”，阶段改为 `dev-implement`，读 `../dev-implement/SKILL.md` 并执行，之后会依次回到这里。修不了的写进简报的“紧急”。
- **警告**：场景没有测试、浏览器测试没做、文档没更新。能补的补上；补不了的写进简报。
- **建议**：记进后续清单。

同一个问题自动返工最多 1 次；第二次还在，就写进“紧急”交给人。

## 3. 验收页

按 preview.md 生成验收页，源文件放在 `pages/accept/`，用到的截图复制到同一目录，按目录上传（同一链接，`-m` 写这一版改了什么）。内容从上到下：

1. **结论一句话**：做完了什么、能不能验收、有什么要注意的。
2. **紧急**：严重问题、阻塞的任务、未修复的安全或数据风险、浏览器测试没做（没有就不显示这一块）。
3. **需要你决定**：所有还没处理的挑战型 `c` 和口味型 `d`（带默认），和终端简报编号一致。
4. **场景对照表**：场景 → 测试 → 结果 → 截图（点开看大图）。
5. **改动概览**：改了哪些模块、多少文件、提交列表。
6. **自动决定**：机械型决定的数量，展开可看列表。
7. **后续清单**：这次没做、以后可以做的改进。
8. **怎么自己试**：本地启动命令、要打开的地址、测试账号从哪个环境变量来。

## 4. 关口 C

按 gates.md 的“关口 B / C”格式给出简报：一句话、页面链接和访问码、紧急、需要决定的 `c`/`d`、其他（测试数和结果、浏览器测试情况、后续清单条数）。状态行写 `待关口：C`，提交，**这一轮结束，等人回复**。

处理回复（按 gates.md）：
- 有要改代码的：按 gates.md“有改动时”的关口 C 部分加返工任务、回到 dev-implement；走完实现 → 测试 → 评审后回到这里，**更新同一个验收页**，重新给出简报。最多 3 轮。
- 只改文档或决定记录的：改完重新给出简报。
- 通过：
  1. 状态改为“已完成”，清空待关口，同步索引，变更记录写一句；
  2. decisions.md 的“关口处理”列补全；
  3. 提交这些文档和 `.dview.json`；
  4. 阶段改为 `dev-cicd`，读 `../dev-cicd/SKILL.md` 并执行（它会把合并、推送、发布这些对外动作列成关口 D）。
