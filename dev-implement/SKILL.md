# 编码实现

按 docs/tasks.md 中的任务清单逐个实现，每完成一个任务更新状态并提交代码。

## 核心原则

1. **一次一个任务**：不跨任务工作，不提前做后续任务的事
2. **最小可运行闭环优先**：先让系统跑起来，再补充细节
3. **小步频繁提交**：每个有意义的改动都提交，不攒大改动
4. **发现偏差先停下**：实现中发现与设计不符，先更新设计文档再继续

## 执行步骤

### 1. 选取当前任务

读取 docs/tasks.md，找到第一个状态为"待办"且所有依赖任务已"完成"的任务。将其状态更新为"进行中"。

如果没有满足条件的任务，检查是否有阻塞原因并告知用户。

### 2. 理解任务上下文

在动手写代码前，完成以下准备：

- 重读该任务的描述、涉及文件、完成定义
- 阅读相关的已有代码（依赖任务产出的文件）
- 阅读 docs/design.md 中该任务对应的设计部分
- 确认技术选型和接口约定

### 3. 实现代码

按以下节奏推进：

#### 3.1 搭骨架

- 创建需要的文件和目录结构
- 写出函数/类/模块的签名和空实现
- 确保项目能编译/解析通过（即使功能未完成）

#### 3.2 实现核心逻辑

- 按功能点逐步填充实现
- 每完成一个独立的功能点就提交一次
- 提交信息使用 conventional commits 格式：
  - `feat: 添加用户注册接口` — 新功能
  - `fix: 修复密码校验遗漏空值` — 修 bug
  - `refactor: 提取数据库连接为独立模块` — 重构
  - `test: 添加注册接口单元测试` — 测试
  - `docs: 更新 API 接口文档` — 文档
  - `chore: 添加 eslint 配置` — 工程化

#### 3.3 处理边界与异常

- 补充参数校验、错误处理
- 处理设计文档中提到的异常场景

### 4. 处理设计偏差

实现过程中如果发现以下情况，**必须先停下来**：

- 设计中的接口定义不合理，需要调整
- 发现设计遗漏了某个场景
- 技术选型无法满足某个需求
- 任务之间的依赖关系需要调整

处理方式：

1. 在 docs/design.md 对应位置添加变更说明，格式：
   ```
   > **变更 [日期]**: 原设计为 xxx，实现时发现 yyy，改为 zzz。原因：...
   ```
2. 如果影响其他任务，同步更新 docs/tasks.md
3. 告知用户变更内容，确认后再继续

### 5. 验证任务完成

按该任务的"完成定义"逐条验证：

- 运行完成定义中指定的命令
- 确认输出符合预期
- 如果有自动化测试，确保测试通过

全部通过后，将 docs/tasks.md 中该任务状态更新为"完成"。

### 6. 提交并推进

- 确保所有改动已提交（不留未提交的改动）
- 回到步骤 1，选取下一个任务

## 禁止事项

- **不要**在当前任务中顺手重构其他任务范围的代码
- **不要**提前实现后续任务的功能（即使顺手就能做）
- **不要**在代码中留 TODO 指向当前任务应完成但跳过的内容
- **不要**改变任务的完成定义来迁就实现（如果定义不合理，走设计偏差流程）
- **不要**一次性提交大量改动，保持每次提交聚焦于一个改动点
