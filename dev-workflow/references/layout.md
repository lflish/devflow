# 文件放在哪、状态怎么写

## 目录

每个需求一个文件夹，放在配置的 `docs_dir` 下（默认 `docs/changes/`）：

```
docs/changes/
├── README.md                          所有需求的索引
└── 2026-11-02-review-comments/        <创建日期>-<英文短名>
    ├── spec.md          需求（dev-requirements）；第一行下面是状态行
    ├── design.md        设计（dev-design；规模“小”时没有）
    ├── tasks.md         任务、进度、后续清单（dev-plan / dev-implement）
    ├── decisions.md     裁决记录（各阶段都写）
    ├── test-report.md   测试结果（dev-test，每轮覆盖）
    ├── review.md        评审结果（dev-review，每轮覆盖）
    ├── evidence/        浏览器截图等证据
    └── pages/           要上传到 vibeview 的页面源文件
        ├── prototype/   效果页
        ├── compare-<n>/ 对比页
        ├── plan/        方案简报页
        └── accept/      验收页
```

- 短名用小写英文加连字符，3–5 个词。
- 项目原来有别的需求文档目录（比如 `docs/specs/*.md`），**不要迁移旧文件**。新需求按这里的格式放；`docs_dir` 可以在配置里改。
- `pages/` 放在仓库里，是为了让 vibeview 每次上传同一个路径时更新到同一个链接（见 preview.md）。
- CI 需要的密钥清单放在仓库根目录 `docs/secrets-checklist.md`（项目级，不属于某个需求）。

## 状态行

spec.md 标题下第一行：

```markdown
状态：实现中　阶段：dev-test　待关口：—　规模：标准　创建：2026-11-02　更新：2026-11-03
```

三个字段各管一件事：

| 字段 | 含义 | 谁来改 |
|------|------|--------|
| **状态** | 需求走到哪了，给人和索引看 | 关口通过时改 |
| **阶段** | 正在做哪个 skill，给 AI 续上用 | 每个阶段开始时改成自己；交接时改成下一个 |
| **待关口** | 正在等人回复哪个关口；没有就写 `—` | 发出简报时写上；回复处理完清空 |

### 状态的变化

| 状态 | 什么时候改成它 |
|------|----------------|
| 草案 | 创建 spec 时 |
| 已确认 | 关口 A 通过（规模“小”没有这一步） |
| 实现中 | 关口 B 或 AB 通过；关口 C 打回返工时也改回它 |
| 待验收 | dev-accept 开始时 |
| 已完成 | 关口 C 通过 |
| 已交付 | 关口 D 确认的对外动作全部执行完（在变更记录里写清做了哪些：合并、推送、发布、部署） |
| 搁置 | 人说不做了；写明原因 |

### 待关口的取值

| 值 | 由谁写 | 等的是什么 |
|----|--------|------------|
| 评审 | dev-requirements | 需求评审消息的回复 |
| A | dev-requirements | 关口 A |
| AB | dev-plan（规模“小”） | 合并的需求和方案确认 |
| B | dev-plan | 关口 B |
| C | dev-accept | 关口 C |
| D | dev-cicd | 关口 D |
| 停-<n> | 任何阶段 | 停止情况下的对比页 `compare-<n>` |

## 索引 `README.md`

```markdown
# 需求索引

| 需求 | 状态 | 规模 | 说明 | 更新 |
|------|------|------|------|------|
| [2026-11-02-review-comments](2026-11-02-review-comments/spec.md) | 实现中 | 标准 | 页面批注和确认签字 | 2026-11-03 |
```

每次改“状态”时同步更新这一行。

## `decisions.md` 文件头

```markdown
# 裁决记录 · <需求名>

规则见 dev-workflow/references/decisions.md。

| # | 阶段 | 决定 | 类型 | 依据 | 理由 | 放弃的选项 | 定错的代价 | 关口处理 |
|---|------|------|------|------|------|------------|------------|----------|
```

## 编号

整个需求里统一，避免混淆：

| 前缀 | 是什么 | 在哪 |
|------|--------|------|
| R1、R1.1 | 需求、验收场景 | spec |
| P1 | 前提 | spec |
| E1 | 扩展候选 | 需求评审消息、spec |
| Q1 | 问题 | 需求评审消息、关口 A |
| H1 | 假设（AI 定的） | spec |
| T1 | 任务 | tasks |
| d1 / c1 | 口味型 / 挑战型决定 | decisions |
| X1 | 探索式检查发现的问题 | test-report |
| V1 | 前置验证 | design |

## git

- **dev-requirements 建文件夹时**，如果当前在默认分支（main/master）上，新建本地分支 `change/<短名>` 并切过去。建本地分支、本地提交都不算对外动作，不用问。
- **每个阶段结束时**，提交本阶段的产物（文档、代码、`.dview.json`），提交信息写明阶段，比如 `docs(review-comments): spec and prototype`。
- 合并回默认分支、推送、开 PR 都在关口 D 一次确认（dev-cicd）。
