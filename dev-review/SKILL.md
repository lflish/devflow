# dev-review — 代码评审

## 触发时机

当用户完成一段代码实现、一个功能阶段、或准备合并/发布前，需要对代码进行系统性评审时调用本 skill。

## 执行流程

### 第一步：收集上下文

1. 读取需求文档（docs/requirements*.md 或用户指定文件），明确本次变更的目标与验收标准。
2. 读取设计文档（docs/design*.md、docs/api*.md 等），掌握预期的架构与接口约定。
3. 确定评审范围：
   - 若用户指定了文件/目录，以此为准。
   - 若未指定，用 `git diff main...HEAD --name-only`（或对应基准分支）获取变更文件列表。
4. 逐一读取变更文件的完整内容（不仅是 diff），理解上下文。

### 第二步：逐项检查

按以下清单对每个变更文件进行检查，每条检查结果记录到评审条目中。

#### 2.1 实现与设计一致性

- 接口签名（路径、方法、参数、返回值）是否与设计文档一致。
- 数据模型字段、类型、约束是否与设计一致。
- 业务流程分支是否覆盖设计中描述的所有场景。
- 若存在偏差，判断是设计遗漏还是实现错误，标注到具体行。

#### 2.2 正确性与边界条件

- 核心算法逻辑是否正确，有无 off-by-one、空值、零值、溢出等边界遗漏。
- 并发场景是否安全（竞态、死锁、资源泄漏）。
- 外部依赖调用（数据库、API、文件系统）的错误路径是否处理。
- 状态机/流程是否存在不可达状态或死循环。

#### 2.3 错误处理

- 异常/错误是否被捕获并合理处理，而非静默吞掉。
- 错误信息是否足够定位问题（包含上下文），但不泄露内部细节给终端用户。
- 资源（文件句柄、连接、锁）是否在异常路径中正确释放。
- 重试逻辑是否有退避策略和上限。

#### 2.4 安全

- **注入**：SQL 拼接、命令拼接、模板注入 — 必须使用参数化/转义。
- **密钥硬编码**：搜索代码中的 password、secret、token、api_key 等字面量，不允许出现真实值。
- **权限与暴露面**：API 端点是否有认证/鉴权守卫；文件/目录权限是否最小化；调试端点是否在生产环境关闭。
- **依赖安全**：新引入的第三方包是否有已知漏洞（如有 lock 文件可用 `npm audit` / `pip audit` 快速扫描）。

#### 2.5 可维护性

- 命名是否清晰、一致，遵循项目已有风格。
- 是否存在大段重复代码，可提取公共函数/模块。
- 单个函数/方法是否过长（超过 80 行需关注）或圈复杂度过高（超过 10 需关注）。
- 魔法数字/字符串是否提取为常量。
- 注释是否与代码一致，有无过时注释。

#### 2.6 测试覆盖

- 关键业务路径（正常流程 + 主要异常流程）是否有对应测试用例。
- 边界条件是否有测试。
- 测试是否真正断言了预期行为，而非仅仅 "不报错即通过"。
- 若项目有覆盖率要求，检查覆盖率是否达标。

### 第三步：问题分级与记录

每条发现的问题按以下格式记录：

```
### [阻塞/建议/疑问] 简短标题

- **文件**: path/to/file.ext:行号
- **问题**: 具体描述问题是什么。
- **修改方向**: 建议如何修复或改进。
```

分级标准：

| 级别 | 含义 | 处理要求 |
|------|------|----------|
| **阻塞** | 存在功能错误、安全漏洞、数据丢失风险或严重违反设计 | 必须修改后才能合并，阻塞 CI/CD |
| **建议** | 可改善可维护性、性能或可读性，但不影响正确性 | 建议修改，作者可说明理由后保留 |
| **疑问** | 评审者不确定意图或正确性，需作者解释 | 作者需回复说明 |

### 第四步：产出评审文档

在 `docs/` 目录下生成 `review-YYYY-MM-DD.md`（若同日多次评审则加序号 `-01`、`-02`），结构如下：

```markdown
# 代码评审报告

- **日期**: YYYY-MM-DD
- **评审范围**: 简述本次评审的功能/模块
- **基准分支**: main（或实际基准）
- **变更文件数**: N
- **设计文档**: docs/design-xxx.md（或"无"）

## 评审结论

**结论: 通过 / 修改后通过 / 不通过**

| 统计 | 数量 |
|------|------|
| 阻塞 | X |
| 建议 | X |
| 疑问 | X |

> （若结论为"修改后通过"或"不通过"，在此说明关键原因。）

## 评审详情

### [阻塞] xxx
...

### [建议] xxx
...

### [疑问] xxx
...

## 后续行动

- [ ] 阻塞项 1：xxx（负责人 / 预计完成时间）
- [ ] 疑问项 1：xxx（待作者回复）
```

### 第五步：给出结论与后续指引

- **通过**：无阻塞项，建议项不超过 3 条。告知用户可以进入 CI/CD 阶段。
- **修改后通过**：有阻塞项但均有明确修改方向。告知用户修复后可再次运行评审。
- **不通过**：存在设计层面严重偏差或大面积质量问题。建议回到设计阶段重新对齐。

**关键规则：只要存在任何一条"阻塞"级问题未解决，不得进入 CI/CD 阶段。**

## 注意事项

- 评审要就事论事，定位到具体文件和行号，给出可操作的修改方向，不说"建议优化"这类空话。
- 若没有设计文档可对照，在评审报告开头注明"无设计文档，仅基于代码本身评审"，并将设计一致性检查替换为"代码意图合理性"检查。
- 对于大型变更（超过 20 个文件），优先评审核心业务逻辑文件，配置文件和自动生成文件可略过。
- 评审过程中如果发现需要运行测试来验证某个疑问，应先运行测试再下结论。
