按业界实践把流程定为 5 个阶段，先定每个阶段的约定，再按约定改写 skills。状态：草案，等你确认。2026-11-05

一句话

需求 → 设计 → 开发 → 测试 → 发布。5 个阶段，4 个关口，只有“开发”没有关口。skills 从 9 个减为 7 个：1 个总纲、5 个阶段各一个、1 个通用评审。

为什么是 5 个

理论标准拆得很细，实践中把总是一起做的合并。和网络分层一样：ISO/IEC/IEEE 12207 的 14 个技术过程，就像 OSI 七层；团队日常走的 5 步，就像 TCP/IP 五层。

devflow 阶段ISO/IEC/IEEE 12207 技术过程团队里的叫法
需求业务或使命分析、干系人需求定义、系统/软件需求定义需求评审、PRD
设计架构定义、设计定义、系统分析技术评审、技术方案、排期拆任务
开发实现、（部分）集成编码、自测、代码评审
测试集成、验证、确认提测、QA、验收
发布交付（transition）上线
不在单个需求内运行、维护、退役运维，项目持续在做

每个阶段的约定

每个阶段写清 6 件事。skill 按这里写，不再自己发明边界。

1 需求dev-requirements评审消息（必要时）+ 关口 A
进入条件
有新想法或新需求；或 spec 状态是“草案”
做什么
  1. 定规模，建需求文件夹和本地分支（微小改动直接改，不走流程）
  2. 先查代码和文档
  3. 需求评审：前提挑战、产品方案（含最小可行）、范围模式、缺口扫描
  4. 你 一条评审消息，全部带推荐（没有歧义时跳过）
  5. 写 spec：需求写成“系统必须…”，每条配场景
  6. 子 agent 新人通读检查
  7. vibeview 效果页（有界面或流程时）
产物
spec.md、decisions.md、pages/prototype/
结束于
关口 A 你看：要做 / 不做、关键场景、假设、效果页 → 状态改为“已确认”
小规模
不在这里停，直接进设计；需求和方案合成一次确认（关口 AB）
不做的事
不问代码能查到的；不问实现方法；不悄悄扩大范围；关口前不写产品代码
2 设计dev-design关口 B合并原 dev-design + dev-plan
进入条件
关口 A 通过（小规模：需求写完）
做什么
  1. 选方案：2–3 个做法按原则选，难分高下的记为口味型 d
  2. 技术方案：结构、接口、数据、状态、安全、需求覆盖（小规模只写 5–10 行）
  3. 前置验证：设计依赖的前提实际跑一遍
  4. 测试计划：每个场景分到单元 / 集成 / 浏览器
  5. 拆任务：文件、接口、对应场景、测试断言、完成定义
  6. 子 agent 工程评审（最后跑，审的是方案加任务）
  7. vibeview 方案简报页
产物
design.md（小规模没有）、tasks.md、pages/plan/
结束于
关口 B 你看：方案、待定的 d 和 c、任务数、风险 → 状态改为“开发中”
小规模
关口 AB：需求部分和方案部分一页确认
不做的事
不停下来问“用 A 还是 B”；不为以后可能用到加抽象；不写“处理边界情况”这种空话
3 开发dev-build无关口合并原 dev-implement，并调用 dev-review
进入条件
关口 B 通过；或关口 C 打回后加了返工任务
做什么
  1. 逐个任务：先写测试并确认失败 → 实现 → 跑测试 → 提交 → 记进度
  2. 遇到问题自己裁决并记录，只有 4 种情况停下
  3. 全部任务完成后跑全量单元、集成测试和 lint
  4. 子 agent 调用 dev-review：明确错误先写回归测试再修，其余记成 d / c
产物
代码和提交、tasks.md 进度、review.md
结束于
可提测就自动进入测试，同时满足：① 任务都完成或已标“阻塞” ② 单元、集成测试和 lint 全过 ③ 评审没有未处理的严重问题（修不了的已记成 c） ④ 没有未提交的改动
你参与
0 次（除不可逆、安全敏感、对外动作、需求走不通这 4 种情况）
不做的事
不一次做多个任务；不重构范围外代码；不放松测试来过关；不推送到远程；浏览器测试不在这里写
4 测试dev-test关口 C合并原 dev-test + dev-accept
进入条件
开发阶段“可提测”
做什么
  1. 场景对照表，补齐缺的测试
  2. 浏览器 连远程浏览器（CDP），确认能打开被测服务；连不上退回本机无头浏览器
  3. 浏览器 每个浏览器场景一个 Playwright 测试，提交进仓库，截图留证
  4. 浏览器 探索式检查：表单、导航、空/出错状态、控制台、手机宽度、权限
  5. 修复：先写回归测试 → 最小修复 → 复测 → 提交
  6. 验收核对：完整、正确、一致、干净
  7. vibeview 验收页：结论、紧急、待定的 d / c、场景和截图
产物
浏览器测试代码、test-report.md、evidence/、pages/accept/
结束于
关口 C 你看验收页 → 状态改为“已完成”；要改代码的回复 → 加返工任务，回到开发
修复的评审
测试中的修复，改动超过 5 个文件或改了接口时，再调一次 dev-review（见下方 d3）
不做的事
不改测试迁就错误的实现；不用操作你个人浏览器的工具；不悄悄略过浏览器测试
5 发布dev-release关口 D原 dev-cicd 改名
进入条件
关口 C 通过；或你说“发布”“上线”“部署”
做什么
  1. 了解现有 CI 和部署方式，优先沿用
  2. CI（需要时）：和本地一样跑，CI 里用本机无头浏览器
  3. 你 关口 D：推送、PR、合并、发布、部署、上线后检查，一份清单一次确认
  4. 逐步执行，每步记录；部署交给项目自己的方式
  5. 浏览器 上线后检查
产物
版本、CI 配置（需要时）、上线记录（写在 spec 变更记录里）
结束于
执行完 → 状态改为“已发布”；你回“跳过” → 停在“已完成”
不做的事
不一个一个问；失败时不强推、不删 tag、不手改服务器

贯穿所有阶段

skill做什么谁用
dev-workflow总纲：状态行和续做判断；共用规则（决定分类、6 条原则、4 种停止情况、提问和关口简报格式、配置、vibeview 页面）每个阶段开头先读；你说“继续”时触发
dev-review独立子 agent 评审：两轮清单，明确错误先写回归测试再修，检查被放松的一律交你决定开发阶段调用；你单独说“评审一下这段代码”时只给结果、不改代码
复盘把反复出现的问题沉淀成规则（借鉴 pstack 的 reflect / correct）以后再加（见 d4）

状态跟着阶段走

草案（需求）→ 已确认（设计）→ 开发中（开发）→ 测试中（测试）→ 已完成（等发布）→ 已发布；任何时候可以“搁置”。

状态行仍是三个字段：状态 / 阶段 / 待关口。“阶段”的值改为新的 skill 名。

从现在的 9 个 skill 怎么变

现在改后说明
dev-workflowdev-workflow流程表、状态值、续做判断改成 5 阶段
dev-requirementsdev-requirements基本不变，交接改为 dev-design
dev-design + dev-plandev-design合并；任务模板挪到 dev-design 的参考文件；关口 B 归它
dev-implementdev-build改名；结尾调用 dev-review；定义“可提测”
dev-reviewdev-review保留为通用 skill；在流程里由 dev-build 调用，交回 dev-build
dev-test + dev-acceptdev-test合并；验收核对和验收页挪进来；关口 C 归它
dev-cicddev-release改名，内容不变

已经验证过的东西不动：浏览器测试写法、关口回复规则、决定分类、安装脚本。改完后用独立子 agent 再通读一遍，并更新流程图页面。

需要你拍板（4 个，都有默认）

回 all 全部按默认；或 d1 B 这样改某一条。

d1. 开发阶段的 skill 叫什么

默认 A：dev-build（和“开发”对应，也和 build 阶段的常见叫法一致）

B：沿用 dev-implement　C：dev-develop

d2. 合并掉的旧 skill（dev-plan、dev-implement、dev-accept、dev-cicd）怎么处理

默认 A：直接删除。git 历史里还在，安装脚本会清理失效的链接

B：保留一个版本，只做“请改用 xxx”的转发，下个版本再删

d3. 测试阶段的修复要不要再评审

默认 A：改动超过 5 个文件或改了接口时才再调 dev-review

B：每次修复都评审（更稳，更慢）　C：不再评审（靠关口 C 你看）

d4. 复盘要不要现在就做

默认 A：先不做，等 devflow 真跑过几个需求、有了真实问题再加

B：现在加一个 dev-retro
