# dev-release：发布

目标：**合并凭验证结论，上生产凭用户一次确认。** 项目有自己的发布或部署 skill 时，具体操作交给它，本 skill 只负责前后的检查和确认。

## 开始

1. 先读 `../dev-workflow/SKILL.md` 的“每次开始时”，照做其中第 1–3 步（包括读 `../dev-workflow/references/decisions.md`、`verification.md`）。本阶段还要读同目录下的 `gates.md`。
2. 有当前需求时，状态行“阶段”改为 `dev-release`；状态应为“已验证”（机器关口 C 已放行）或“已合并”（上生产这一步）。
3. **独立模式**：没有需求文件夹（用户只是要“搭个 CI”“发个版”）时，项目有自己的发布 skill 就直接交给它；没有就照常做下面的步骤，不读写需求文件；没有验证结论的，合并前先说明这一点，按用户的要求处理。
4. **记数据**（metrics.md）：阶段开始、结束；合并前复验的结论；合并、上线各记一行（合并后的这些行随写回一起提交）。

**接着做**：看 spec 变更记录里发布做到哪一步（每步做完都会记一句），从下一步继续。

## 1. 了解现状

- `.devflow.yml` 的 `commands`、`release`、`environments`。
- 已有的 CI（`.github/workflows/`、`.gitlab-ci.yml`、`Jenkinsfile` 等）、发布和部署方式（脚本、Dockerfile、项目自己的发布 skill）。
- **合并会不会自动触发生产部署**：看 CI 里有没有“推到默认分支就部署生产”的工作流。有的话，第 3 步的合并就等于上生产，要放到第 4 步一起确认。
- 分支和远程：当前分支、默认分支、`git remote -v`、能不能用 `gh` 等平台命令。

**已有的东西优先沿用和补充，不要覆盖。**

## 2. CI（没有或不完整时才做）

CI 跑的和本地一样：安装 → lint → 测试 → 构建 → 浏览器测试，任何一步失败就停。
- 命令全部用 `.devflow.yml` 的 `commands`。
- 浏览器测试在 CI 里用本机无头浏览器：不设 `DEVFLOW_BROWSER_CDP`，测试会自动改用本机浏览器；用 Playwright 的 `webServer` 启动被测服务；先 `npx playwright install --with-deps chromium`。
- 构建完把产物真正启动起来做冒烟检查（打开首页、调一个健康检查接口），不只跑单元测试；任何一步失败都打印服务日志的最后几十行。
- 失败时上传截图和 trace。
- CI 里 `safety_valves` 全部关闭，不访问真实的外部服务和付费服务。
- 密钥只用 CI 平台的 secrets，在 `docs/secrets-checklist.md` 列变量名和用途（不写值）。
- **不要加“合并就自动部署生产”的步骤**；部署生产始终走第 4 步的确认。

没有任何现成方式时，参考 [references/github-docker-example.md](references/github-docker-example.md)（示意，不能直接用）。改完先在本地按顺序跑一遍。CI 改动是验证之后加的：按 verification.md 规则 4 复验一次（指纹会变），并在汇总里列出。

## 3. 推送、开 PR、合并

**合并的前提**（任何一条不满足就不合并，停在“已验证”，写进汇总的“等你决定”）：
- tasks.md 里没有“阻塞”的任务；
- 没有未决的 `c<n>`（包括放松检查）；
- 验证结论是“通过”或“通过，有备注”。

步骤：
1. 推送 `change/<短名>` 分支，开 PR 到默认分支。标题用约定格式，正文固定三段：
   - **解决什么问题**：目标、完成条件，关联的 Issue；
   - **怎么验证的**：实际跑过的检查和结果、验证结论和验证者、汇总页链接；**没跑的检查写明原因**；页面改动附截图；
   - **兼容与使用影响**：配置、数据库迁移、公开接口、升级步骤（同时写进 `upgrade_doc`）；没有就写“无”。
   没有远程仓库时跳过，改为本地合并。
2. 用 `gh pr checks --watch`（或对应平台的命令）等 CI。CI 失败：按 dev-build 的做法修复、提交、再推送；同一个问题失败 3 次就停下报告用户。
3. **检查结论还覆盖要合并的代码**：按 verification.md 的“代码指纹”命令，对 PR 当前的头算一遍，和 verdict.md 里的比较；同时看默认分支有没有前移、PR 有没有变基。不一致就按规则 4 复验，结论更新后再继续。
4. **合并**：
   - 合并会自动部署生产的 → 不在这里合并，放到第 4 步一起确认；
   - **L1**：发汇总请用户确认合并，状态行写 `待关口：合并`，这一轮结束；收到回复后**重新做一次第 3 小步**再合并；
   - **L2 / L3**：直接合并（`gh pr merge --squash` 或项目惯例）。
   合并后读回 PR 状态，确认真的合并了（进了合并队列或开了自动合并都不算）。
5. **写回状态**：按 decisions.md 的“写回默认分支”，提交只改 `docs_dir` 下文件的更新（状态“已合并”、变更记录、索引、metrics.md 里“合并”这一行）。不要切换用户主目录的分支。更新汇总。

**L3 一批需求**：每个需求只做到这一步（已合并；合并会自动部署生产的，停在“已验证”），全部需求都到了这一步后，再出**一份**合并的上生产清单（包括那些待合并的 PR）。

## 4. 上生产：一次确认

`release` 里没配发布和部署、合并也不会自动部署的，到这里结束：变更记录写“不上生产”，阶段清空。

否则把要做的动作列成一份清单，**只确认这一次**（所有自主等级都要确认）：

```markdown
## 上生产确认 · <需求名，或这一批的需求列表>

**一句话**：发布 1.4.5 并部署到生产
要执行的动作：
1. （只在合并会自动部署生产时）合并 PR #42 —— 合并即部署生产
2. 发布 1.4.5（按 release.publish：使用 $release 发布 1.4.5）
3. 部署到生产（按 release.production：使用 $deploy-view 部署 v1.4.5）
4. 上线后检查：打开线上首页，确认版本号是 1.4.5；看部署之后的错误日志有没有新增（都是只读）
回滚方式：…

回复 `all` 执行全部；或 `只到 1`、`跳过`（不上生产，停在已合并）。
```

- 版本号按 `release.bump` 升（默认补丁号），`{version}` 是版本号，`{tag}` 是 `release.tag_prefix` + 版本号。
- 状态行写 `待关口：上生产`，**这一轮结束，等用户回复**。这一步只认 `all` 或明确的动作编号；“继续”不算确认。

## 5. 执行和上线后检查

清空待关口，按用户确认的范围逐步执行，每一步做完在 spec 变更记录里写一句（合并后的记录按第 3 步第 5 小步的方式写回默认分支）。清单里有“合并 PR”时，先按第 3 步第 3 小步再检查一次结论，然后合并、读回确认、写回状态，再做后面的动作：
- 发布和部署交给项目自己的方式，**遵循它自己的规则**（预演、备份、健康检查、回滚）。
- 任何一步失败，不要自行用破坏性手段补救（强推、删 tag、手动改服务器），停下来报告。
- 上线后检查：在 production 环境**只读**地检查（按 `post_check`；有测试浏览器时打开线上地址截图），并看一眼部署之后的错误日志有没有新增（项目验证 skill 里写了怎么看）；不提交表单、不写数据。发现新错误时写进汇总；**严重**（出现新的 5xx、进程崩溃或反复重启、错误数明显高于部署前）的按“失败”停下报告，并在报告里给出回滚方式。

完成后：状态改为“已发布”，阶段清空，同步索引，更新汇总：发布了什么版本、检查结果、回滚方式。用户回“跳过”时：已合并的停在“已合并”，没合并的（合并会自动部署的情况）停在“已验证”；变更记录写“不上生产”，阶段清空。
