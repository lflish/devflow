# 需求缺口清单

逐类检查 spec 草稿（或用户的描述），每类标“清楚 / 部分 / 缺失”。只有“部分”和“缺失”需要处理，而且只处理会改变要做的东西或验收方式的那些。

## 目标与范围
- 为什么要做：现在的痛点是什么，现在是怎么绕过去的
- 做完了怎么判断“做对了”
- 本次明确不做什么（容易被误以为要做的那些）
- 有几类用户/角色，各自能做什么

## 数据
- 涉及哪些东西（实体），各有哪些字段，彼此什么关系
- 什么算“同一个”（唯一性）；能不能重复
- 状态怎么变化（创建 → … → 删除），哪些变化不可逆
- 数据量大概多大；要不要分页
- 删除后怎么办：真删、软删、关联数据怎么处理

## 交互和流程
- 关键流程的每一步
- 空状态、加载中、出错、无权限时显示什么
- 重复操作（连点两次、刷新、返回）会怎样
- 手机上能不能用；要不要多语言

## 非功能
- 性能：有没有明确的时间或数量要求
- 安全和隐私：谁能看到什么；有没有敏感数据；要不要记录操作日志
- 可靠性：失败了能不能重试；会不会丢数据
- 兼容性：要支持哪些浏览器、系统、旧版本数据

## 外部依赖
- 依赖哪些外部服务或接口；它们不可用时怎么办
- 导入导出的格式
- 和已有功能、已有接口是否兼容

## 异常和边界
- 非法输入、超长输入、特殊字符
- 并发：两个人同时改同一个东西
- 限流、配额、超时
- 网络慢、请求中途失败、页面停留很久后数据已过期
- **不能静默失败**：每种失败，用户看到什么、管理员能不能查到

## 上线
- 能不能分批上线、出问题怎么回滚
- 要不要迁移已有数据；迁移失败怎么办
- 上线后怎么确认它在正常工作（日志、统计、告警）

## 措辞
- 有没有含义不清的词（“好用”“快速”“稳定”“智能”）→ 量化，或删掉
- 同一个东西有没有用了两个名字 → 统一

## 验收
- 每条需求能不能写出可以检验的场景
- 有没有“做完”的明确标准
