# 测试

为已实现的功能编写测试并验证，确保每条验收标准都有对应测试覆盖。

## 执行步骤

### 1. 梳理测试范围

读取以下文件确定测试范围：

- **docs/requirements.md**：提取全部验收标准（AC），编号为 AC1, AC2, AC3…
- **docs/tasks.md**：确认哪些任务已完成，测试范围仅覆盖已完成的任务
- **docs/design.md**：了解模块边界和接口约定，确定集成测试点

产出一张映射表：

| 验收标准 | 对应测试用例 | 测试层级 |
|----------|-------------|---------|
| AC1: ... | test_xxx    | 单元    |
| AC2: ... | test_yyy    | 集成    |

**每条验收标准必须至少有一个对应测试用例。** 如果某条无法测试，在映射表中注明原因。

### 2. 分层编写测试

按三个层级组织测试：

#### 2.1 单元测试（核心逻辑）

- 覆盖目标：纯函数、核心算法、数据转换、业务规则
- 每个用例包含：
  - **明确的输入**：具体的参数值，不用随机数据
  - **明确的预期输出**：精确到值，不用模糊断言
  - **边界场景**：空值、零值、极大值、非法输入、类型边界
  - **异常场景**：预期抛出的错误类型和消息

```
示例结构（伪代码）：
test "计算订单总价 - 正常情况"
  input: items=[{price:100, qty:2}, {price:50, qty:1}]
  expect: 250

test "计算订单总价 - 空列表"
  input: items=[]
  expect: 0

test "计算订单总价 - 负数价格抛异常"
  input: items=[{price:-1, qty:1}]
  expect: throws InvalidPriceError
```

#### 2.2 集成测试（组件协作）

- 覆盖目标：模块之间的交互、数据库读写、外部服务调用
- 关注点：
  - 数据在模块间传递是否正确
  - 数据库操作的完整流程（写入→读取→验证）
  - 错误在模块间的传播是否符合预期

#### 2.3 冒烟测试（主流程端到端）

- 覆盖目标：用户核心使用路径，从入口到出口的完整流程
- 数量少（3-5 个），覆盖最关键的用户场景
- 验证系统整体可用，不深入细节

### 3. 测试代码规范

- 测试文件放在项目约定的测试目录中（如 `tests/`、`__tests__/`、`*_test.go` 等，跟随项目已有约定）
- 测试函数命名清晰：`test_<被测功能>_<场景>_<预期结果>`
- 不依赖测试执行顺序，每个用例独立可运行
- 测试数据在用例内部定义，不依赖外部状态
- 需要外部依赖（数据库、文件系统）时，在 setup/teardown 中准备和清理

### 4. 运行测试

测试必须能用**一条命令**全部跑完。确定命令后告知用户：

```bash
# 示例
npm test
pytest tests/
go test ./...
cargo test
```

运行测试并记录结果。

### 5. 处理失败

测试失败时，按以下顺序排查：

1. **先看是不是测试用例写错了**：输入或预期输出不正确
2. **再看是不是实现有 bug**：代码逻辑与设计不符
3. **最后看是不是设计有问题**：设计本身的逻辑矛盾

**原则：不要修改测试用例来迁就错误的实现。** 如果实现确实有 bug，修复代码而不是改测试。只有确认测试本身的预期不合理时才调整用例。

如果发现是实现的 bug：
- 修复代码
- 重新运行全部测试（不仅是失败的那个）
- 确认修复没有引入新的失败

### 6. 输出测试结论

所有测试跑完后，输出以下结论：

```markdown
## 测试结论

**运行命令**: `xxx`
**运行时间**: xx 秒

### 结果汇总

| 类别 | 通过 | 失败 | 跳过 | 合计 |
|------|------|------|------|------|
| 单元测试 | x | x | x | x |
| 集成测试 | x | x | x | x |
| 冒烟测试 | x | x | x | x |
| **合计** | **x** | **x** | **x** | **x** |

### 验收标准覆盖

| 验收标准 | 状态 | 对应用例 |
|----------|------|---------|
| AC1: ... | 通过 | test_xxx |
| AC2: ... | 通过 | test_yyy |
| AC3: ... | 未覆盖 | 原因：... |

### 未覆盖项及原因

- AC3 未覆盖：需要外部支付沙箱环境，当前不可用（示例）

### 发现的问题

- （列出测试中发现并已修复的 bug，无则写"无"）
```

将此结论追加到 docs/tasks.md 对应里程碑的末尾，作为该阶段的质量记录。
