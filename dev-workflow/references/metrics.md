# 数据记录：devflow 到底有没有用

规则和 skill 越加越多，要用数据判断它们值不值。每个需求记一份 `metrics.md`（在需求文件夹里），**只追加，不修改**；积累几个需求后汇总成一页统计。

## 记什么

一个事件一行，发生时立刻用 [devflow_record.py](../scripts/devflow_record.py) 记（Python 3 标准库；`<dev-workflow>` 是 dev-workflow skill 目录的绝对路径）：

```bash
python3 <dev-workflow>/scripts/devflow_record.py metric --dir <需求文件夹> \
  --phase dev-test --event 机器关口 --value "C 通过" --note "第 1 轮；验证者 codex"
```

脚本自动取时间，校验阶段和事件名，文件还没有时建好表头。`--phase` 只能是 dev-requirements、dev-design、dev-build、dev-test、dev-release、合并后；`--event` 只能是下面事件表里的名字。

**收到用户回复后，第一个动作就是记“用户回复”**（在读文件、跑命令之前），否则后面的工作会把时间推后。不给 `--value` 时，脚本自动算距上一条“问用户”的分钟数。

记错了不要改旧行，追加一行“更正”。谁在做哪个阶段，谁就记那个阶段的事件（各阶段 SKILL.md 里写了在哪一步记什么）。没有 python3 时才手写，时间取实际时间，阶段、事件、值严格按下表的写法。

```markdown
# 数据记录 · <需求名>

| 时间 | 阶段 | 事件 | 值 | 说明 |
|------|------|------|----|------|
| 2026-11-08 10:02 | dev-requirements | 阶段开始 | | 规模：标准，等级：L2 |
| 2026-11-08 10:15 | dev-requirements | 问用户 | 评审消息 | 3 个前提、2 个方案、3 个问题 |
| 2026-11-08 10:31 | dev-requirements | 用户回复 | 16 分钟 | all |
| 2026-11-08 11:40 | dev-design | 机器关口 | B 通过 | 第 1 轮；验证者 claude |
| 2026-11-08 14:05 | dev-test | 机器关口 | C 不通过 | 第 1 轮；拦下 2 个问题（X1、X2） |
| 2026-11-08 14:50 | dev-test | 机器关口 | C 通过 | 第 2 轮 |
| 2026-11-08 15:10 | dev-release | 合并 | | PR #42 |
| 2026-11-12 09:00 | 合并后 | 合并后发现问题 | 1 | 移动端按钮错位，见 2026-11-12-fix-comment-button |
```

事件只用这几种（`值` 一栏的写法）：

| 事件 | 什么时候记 | 值 |
|------|------------|----|
| 阶段开始 / 阶段结束 | 每个阶段进入、交接时 | 空 |
| 问用户 | 发出需要回复的简报或问题时 | 关口名或问题类型 |
| 用户回复 | 收到回复时 | `<n> 分钟` = 回复时刻 − 最近一条“问用户”的时刻（脚本自动算）；前面没有“问用户”（比如 L2 下回复汇总里的 d/c）就留空 |
| 机器关口 | 每次得出结论时 | `B`、`C`、`合并` 之一 + 空格 + `通过`、`通过，有备注`、`不通过` 之一（如 `C 通过，有备注`），说明里写第几轮、验证者 |
| 验证拦下问题 | 验证或评审拦下有证据的问题时。待验证项不计入，复现后才计 | 个数（整数） |
| 返工 | 加返工任务时 | 任务数（整数） |
| 原型实验 | 用原型或实验代替提问时（decisions.md 第一节） | 实验个数（整数） |
| 用量 | 每次派验证者、调用其他模型、用云浏览器后 | 例如 `验证者 1 轮`、`codex 3 次`、`云浏览器 4 分钟`；用来对照 `budget` |
| 合并 / 上线 | 合并、上生产完成时（事件名分别是 `合并`、`上线`） | 空 |
| 合并后发现问题 | 之后修 bug 时，查出是这个需求引入的（阶段写 `合并后`） | 个数（整数），说明里写新需求的短名 |
| 更正 | 之前某一行记错时 | 正确的内容，说明里写更正的是哪一行 |

“合并后发现问题”记在**原来那个需求**的 `metrics.md` 里，按 [decisions.md 的“写回默认分支”](decisions.md#写回默认分支) 检查生产影响并处理。dev-requirements 判断是在修 bug 时（包括不建文件夹的微小修复），会用 `git log` / `git blame` 查是哪个需求引入的。这是衡量机器验证是否靠谱的关键数据。

合并之后才发生的事件（合并、上线）写在需求文件夹里，随 dev-release 的写回一起提交。

## 怎么看

- 汇总页（preview.md）最下面显示这个需求的小结：总耗时、等用户的时间、问了用户几次、机器关口各几轮、拦下几个问题。
- 用户说“统计一下 devflow 的效果”“看看数据”时：读所有需求的 `metrics.md`，生成一页统计（按 preview.md 上传或留在本地），至少包括：
  - 每个需求：规模、等级、总耗时、问用户次数、等用户的总时长、机器关口轮次、验证拦下的问题数、合并后发现的问题数；
  - 平均值和趋势（按时间顺序）；
  - **逃逸率 = 合并后发现的问题 ÷（验证拦下的问题 + 合并后发现的问题）**：越低越好，说明机器验证越靠谱；
  - 规则的使用情况：哪些情况下用了原型实验、哪些 `c` 最常出现。
- 以后要做“用 / 不用 devflow”的对照实验，也用这些字段，好比较。

不估算 token 和费用，除非工具能直接给出准确数字。
