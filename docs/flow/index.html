共用规则（dev-workflow/references）

每个阶段开头都先读 ../dev-workflow/SKILL.md 和 decisions.md，所以下面这些规则在所有阶段都生效。

遇到要做决定的事：先分类

机械型

只有一个合理答案：文件放哪、命名、用项目已有的库。

直接定，重要的记一行。

口味型 d1, d2…

两个方案都合理；范围在边界上；评审意见有道理。

先按推荐定、继续做，攒到下一个关口给你看，你可以改。

挑战型 c1, c2…

要改你定下的需求、范围、方案，或想放松某个检查。

绝不自己改，按原样继续，到关口单独列出：原来怎样、建议怎样、理由、改错的代价。

决策原则（按顺序）

  1. 以 spec 为准
  2. 复用已有
  3. 直白优先
  4. 影响范围内补全（只限本来就要改的文件）
  5. 不扩大范围（记进“后续”）
  6. 倾向行动

只有这 4 种情况中途停

  1. 不可逆或破坏性操作
  2. 安全敏感操作
  3. 对外副作用（推送、发布、部署）→ 一般攒到关口 D
  4. spec 根本走不通 → 生成 vibeview 对比页让你选

不算停止情况：上传 vibeview、连测试浏览器、本地提交和建分支、装测试依赖、启停本地服务。

关口回复怎么写

  • all 全部按默认
  • d2 B　c1 同意
  • Q3 B　H2 改为 …　E1 加入　P1 不同意：…
  • 问 d3　重做 <原因>
  • 同一个关口最多来回 3 轮

状态和续做：换了会话也能接着做

每个需求的 spec.md 标题下有一行状态，AI 每次开始都先看它：

状态：实现中　阶段：dev-test　待关口：—　规模：标准　创建：2026-11-02　更新：2026-11-03

状态（给你看）

草案 → 已确认 → 实现中 → 待验收 → 已完成 → 已交付；也可以是“搁置”。

阶段（给 AI 续做）

正在做哪个 skill。每个阶段开始时改成自己，交接时改成下一个。

待关口（在等你）

评审 / A / AB / B / C / D / 停-n。有值时，你说“继续”，AI 会把那个关口的简报重发给你，而不是重做。

状态怎么变，哪里会回头

“继续”时 AI 怎么判断从哪里接着做

顺序看到做什么
1“待关口”有值你的消息是回复 → 按关口规则处理；不是 → 重发那个关口的简报
2“阶段”有值读那个阶段的 SKILL.md，从它写的“接着做”处继续
3没有需求文件夹当作新需求，进入 dev-requirements
