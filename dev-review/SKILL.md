# dev-review：评审

目标：**用一双新的眼睛找出写代码的人看不到的问题；只认跑得出来的问题；能修的修，不能定的交给用户。**

## 开始

1. 先读 `../dev-workflow/SKILL.md` 的“每次开始时”，照做其中第 1–3 步（包括读 `../dev-workflow/references/decisions.md` 和 `verification.md`）。
2. 判断方式：
   - **在流程里**：由 dev-build 调用，有需求文件夹。阶段不改（仍是 `dev-build`）。
   - **独立模式**：用户直接要求评审，或找不到需求文件夹。范围按用户说的；没有 spec 就在结果开头写“无需求文档，只按代码本身评审”，把一致性检查换成“代码意图是否合理”。**不直接改代码**，只给出结果，按严重程度列出，每条带证据和改法，问用户要修哪些。不写 review.md。

**接着做**：已有本轮 review.md 时，从还没处理的问题继续。

## 1. 确定范围

- 基准：当前分支和默认分支的分叉点，`git merge-base HEAD main`（默认分支不是 main 时用实际的）。
- 改动文件：`git diff --name-only <基准>...HEAD`，加上未提交的改动（正常情况下应该没有）。
- 自动生成的文件、锁文件、截图不评审内容。

## 2. 独立评审

按 verification.md 的“验证者用哪个模型”选评审者（优先同级别的其他模型，不可用时用同一模型的全新子 agent），提示词用 [references/reviewer-prompt.md](references/reviewer-prompt.md)，清单是 [references/checklist.md](references/checklist.md)。
改动很大（超过 20 个文件）时，可以按模块分给 2–3 个评审者并行。
没有任何子 agent 或其他模型可用时，自己按清单逐项检查，并在报告里注明“评审由同一上下文完成”。

## 3. 处理每个问题

先看证据：评审者给出的每个问题，**自己先按它的命令跑一遍**。跑出来了才算问题；跑不出来、或者只是“看起来有风险”的，不采纳，写一行理由。

| 类别 | 处理 |
|------|------|
| 明确错误（有证据、改法清楚） | **直接修**：先写能复现它的测试并确认失败，再修，再跑测试。每个修复单独提交，`fix:` 开头 |
| 取舍 | 按决策原则定。决定改就改；不改写一行理由。记口味型 `d<n>` |
| 需求问题、只有人能做的事 | 不改需求，记 `c<n>` |
| 检查放松 | **不自动处理**，记 `c<n>`，写清放松了什么、看到的理由 |
| 评审者错了 | 不采纳，写一行理由 |

修复后重新运行单元、集成测试和 lint，附上输出。修复改动较大（超过 5 个文件，或改了接口）时，对新的改动再评审一次，最多一次。

## 4. review.md

```markdown
# 评审：<需求名>

日期：YYYY-MM-DD　范围：<基准>..<HEAD>，N 个文件　评审者：<模型>（<为什么是它>）

结论：无未处理的严重问题 / 有未处理的严重问题（见下）

| 统计 | 严重 | 一般 |
|------|------|------|
| 已修复 | | |
| 交给用户决定 | | |
| 不采纳 | | |

## 已修复
- [严重] 文件:行号 问题（证据：命令和输出）→ 怎么修的（提交 abc123，回归测试 xxx）

## 交给用户决定
- d4 [一般] …（已按 A 做）
- c2 [严重] 检查放松：… 看到的理由：…（推荐：恢复原检查）

## 不采纳
- [一般] … 理由：跑不出来 / …

## 测试复跑
命令和结果
```

**在流程里**：提交 review.md 和修复，回到 dev-build 的第 3 步继续（读 `../dev-build/SKILL.md`）。

## 规则

- 每个问题定位到文件和行号，附证据和可执行的改法；“建议优化”这种空话不算问题。
- 不确定的先运行或读代码确认，不凭感觉下结论。
- 未处理的“严重”问题会挡住“可提测”；修不了的必须记成 `c<n>`，写进汇总的最前面。
