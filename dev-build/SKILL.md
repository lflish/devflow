# dev-build：开发

目标：**把任务连续做完，中途不打扰用户；以“可提测”结束。** 这个阶段没有人工关口。

## 开始

1. 先读 `../dev-workflow/SKILL.md` 的“每次开始时”，照做其中第 1–3 步（包括读 `../dev-workflow/references/decisions.md`）。
2. 前提：spec 状态是“开发中”（机器关口 B 已放行、小规模关口 A 已通过，或因返工回来）。状态是“草案”“已确认”的，说明方案还没过，回到 dev-design（小规模回到 dev-requirements）。
3. 状态行“阶段”改为 `dev-build`。
4. 确认在 `change/<短名>` 分支上（dev-requirements 已建；没有就 `git switch -c change/<短名> <默认分支>`）。
5. **独立模式**：没有需求文件夹、用户只是让你写一段代码时，照常写代码和测试，不读写 tasks.md，不交接。
6. **记数据**（metrics.md）：阶段开始、结束；因返工回来时记“返工”和任务数；评审拦下的有证据的问题记“验证拦下问题”；原型实验。

**接着做**：读 tasks.md 的“进度”和 decisions.md 最后几行，从第一个“进行中”或“待办”的任务继续；任务都做完了就从第 3 步继续。

## 1. 每个任务

1. **选任务**：第一个“待办”且依赖都已完成的任务（“进行中”的优先，说明上次没做完）。改成“进行中”。
2. **读上下文**：任务描述、接口、对应场景；design.md 相关部分；要改的文件和周围的代码。
3. **先写测试**：按任务里列的单元、集成测试名和断言写。浏览器层的测试不在这里写（由 dev-test 写），但要按任务要求加好 `data-testid`。
4. **运行，确认它失败**，而且是因为功能还没实现而失败，不是因为测试写错、导入错误。
5. **实现**：写让测试通过的最少代码。遵循项目惯例和 `.devflow.yml` 的 `rules.build`。
6. **运行这个任务的测试**，再运行相关的全部测试，确认没有破坏别的东西。
7. **按完成定义验证**：运行完成定义里的命令，核对输出。
8. **提交**：只提交这个任务的改动，提交信息用约定格式（`feat:` `fix:` `refactor:` `test:` `docs:` `chore:`）。
9. **记录**：任务改为“完成”，在“进度”表追加一行（时间、提交、测试结果）。和提交同时做。

然后马上做下一个任务。**任务之间不停顿、不汇报进度、不问“要继续吗”。**

## 2. 遇到问题时：裁决，不停等

| 遇到 | 怎么做 |
|------|--------|
| 想问“这样做行不行” | 能跑出答案的，写个探针跑一下（decisions.md 第一节） |
| 计划里的接口不合理、漏了一步 | 按决策原则改，记一行；影响后面任务的，同步改 tasks.md |
| 设计和实际代码对不上 | 以 spec 为准调整做法，在 design.md 的“变更”里写一行，decisions.md 记一行 |
| spec 有歧义 | 选最符合 spec 目的的理解，记口味型 `d<n>` |
| 觉得需求该改、或碰到“只有人能做的事” | 按原需求做其余部分，记 `c<n>`，受影响的任务标“阻塞”（写明等哪个 `c`） |
| 发现范围外的改进机会 | 记进 tasks.md 的“后续”，不做 |
| 测试失败 | 先查测试是否写错，再查实现，最后查设计。修实现，不改测试迁就实现 |
| 原因不明显的问题（性能、偶发失败、“为什么不对”） | 不要一个修法接一个修法地试：先做能反复运行的验证脚本，留下“改之前”的数据，列 2–4 个假设，各做一个实验，按数据决定改哪里（decisions.md 第一节第 3 条） |
| 同一个问题试了 3 次还不行 | 任务标“阻塞”，写清现象和试过什么，先做不依赖它的任务；依赖它的也标“阻塞” |

## 3. 全部任务做完后

“没有待办、也没有进行中”的任务时（剩下的都是“完成”或“阻塞”）：
1. 运行全部单元、集成测试和 lint（`.devflow.yml` 的 `commands`），附上输出。
2. **独立评审**：读 `../dev-review/SKILL.md`，按它的“在流程里”方式执行。它会修掉有证据的明确错误，把其余的记成 `d`/`c`，写好 review.md 后回到这里。
3. 评审修过代码的，重新运行第 1 步。

## 4. 可提测

同时满足这 4 条，就是可提测：
1. 任务都是“完成”或“阻塞”（阻塞的都写明了原因；注意：有阻塞任务的需求可以测试和验证，但不能合并）；
2. 单元、集成测试和 lint 全部通过（附本轮的输出）；
3. review.md 里没有未处理的“严重”问题（修不了的已记成 `c<n>`）；
4. 没有未提交的改动。

满足后：状态改为“测试中”，阶段改为 `dev-test`，提交，然后读 `../dev-test/SKILL.md` 并执行。

任务全部被同一个 `c<n>` 卡住、没有任何可做的工作时，按 gates.md 发汇总，状态行写 `待关口：<c 编号>`，这一轮结束。

## 不要做的事

- 不要一次做多个任务，也不要提前做后面任务的事。
- 不要做重构，也不要改任务范围以外的文件（决策原则 4 允许的补全除外）。
- 不要留指向本该在当前任务完成的 `TODO`。
- 不要删测试、跳过测试、放宽断言、调大超时、加忽略规则来让检查通过。确实需要时，记 `c<n>`。
- 不要改任务的完成定义来迁就实现。
- 不要推送到远程：推送在发布阶段处理。
