# 决定怎么做：分类、原则、停止条件、记录

关口之间，AI 会遇到很多需要做决定的地方：方案选哪个、spec 没写到的细节、计划里的漏洞、评审意见要不要采纳……
**这些都由 AI 自己定，不停下来等人。** 定错了，人在下一个关口能看到、能撤回；停下来等人，会耽误人一整天。

## 一、每个决定先分类

| 类型 | 是什么 | 处理 |
|------|--------|------|
| **机械型** | 只有一个合理答案：文件放哪、命名、用项目里已有的库、按项目惯例写 | 直接定。重要的记一行，琐碎的不用记 |
| **口味型** | 两个以上方案都合理，取舍不同；范围在边界上；独立评审的意见和你不同、但有道理 | 先按推荐定下来**继续做**。记一行，编号 `d<n>`，到下一个关口列给人，人可以改 |
| **挑战型** | 你认为应该改变人定下的东西：需求、范围、验收场景、已确认的方案；或者想放松某个检查 | **不自己改**，按人原来定的继续做（做不下去就做不受影响的部分）。记一行，编号 `c<n>`，到下一个关口单独列出 |

拿不准是口味型还是挑战型时，按挑战型处理。

## 二、决策原则（自己做决定时按这个顺序）

1. **以 spec 为准**：spec 写了的照做；计划是对 spec 的展开；两者都没写的，才靠下面几条。
2. **复用已有**：项目里已有的函数、库、模式，优先用，不重复造。
3. **直白优先**：选一个新人一眼能看懂的写法。十行直白的代码好过两百行的抽象。
4. **影响范围内补全**：**当前任务或当前修复本来就要改的文件**里，和这次改动直接相关的明显缺口（漏了错误处理、漏了边界情况），顺手补上，不引入新依赖。这是对“最小改动”的唯一放宽：不为补全而去改其他文件，也不做重构。
5. **不扩大范围**：超出第 4 条的改进，记进 `tasks.md` 末尾的“后续”清单，不做。
6. **倾向行动**：有顾虑就记下来，继续往前走，不卡住。

设计阶段第 2、3 条优先；实现阶段第 3、4 条优先。

## 三、只有这 4 种情况可以停下来问人

1. **不可逆或破坏性操作**：删除数据、改生产数据库、`git push --force`、删分支、`rm -rf` 项目以外的东西。
2. **安全敏感操作**：处理真实密钥或凭据、改权限或认证配置、关闭安全检查。
3. **对外的副作用**：推送到共享分支、开 PR、合并、发布、部署、发消息、调用会产生费用或通知的外部服务。
4. **spec 根本走不通**：每条路都只能靠猜，而且猜错的代价很大，比如核心需求自相矛盾、依赖的外部服务根本不存在。

第 3 种不必单独停：攒到关口 D 一次确认（dev-cicd）。
第 4 种停下来时，按 [questions.md](questions.md) 的格式问，并按 [preview.md](preview.md) 生成**对比页**，状态行写 `待关口：停-<n>`，让人看了图回一个字母就能继续。

**以下都不是停下来的理由**：“要不要继续”、汇报进度、“我做了个决定想确认一下”、发现小问题、计划有小漏洞、测试失败、评审有意见。这些都用分类和记录处理。

### 这些动作不算停止情况，直接做

- 用 dview 上传页面（默认带访问码保护），读取 `DVIEW_TOKEN`
- 连接配置好的 CDP 浏览器，打开被测服务
- 从环境变量读测试账号（不打印出来）
- 建本地分支、本地提交
- 安装开发和测试依赖（`npm i -D`、`pip install -r requirements-dev.txt` 等），下载测试用浏览器（`npx playwright install chromium`）
- 启动、停止本地开发服务
- 在本机建立到已配置主机的 SSH 隧道（`browser.ssh_host`，见 dev-test 的 browser.md）

### 允许问人的例外（除 4 种停止情况外，只有这些）

1. 开头找不到当前需求：有多个未完成的需求，看不出用户指的是哪个。
2. 需求评审消息（dev-requirements）：一轮；人不同意前提、且影响大时，最多再追问一轮，只问受影响的部分。
3. 关口简报（A、AB、B、C、D）。
4. 关口 D 之后执行对外动作时失败（CI 同一问题失败 3 次、部署失败）：停下报告，不自行用破坏性手段补救。

## 四、裁决记录

每个需求一份 `decisions.md`（在需求文件夹里）。每个记录在案的决定一行，**做完决定立刻记**，不要攒到最后：

```markdown
| # | 阶段 | 决定 | 类型 | 依据 | 理由 | 放弃的选项 | 定错的代价 | 关口处理 |
|---|------|------|------|------|------|------------|------------|----------|
| 1 | 设计 | 评论存 SQLite 新表 | 机械 | 原则2 | 项目已用 SQLite | 存 JSON 文件 | 低 | — |
| d1 | 设计 | 评论按页面版本隔离 | 口味 | 原则1 | spec 要求评论对应版本 | 跨版本共享 | 中：要迁移数据 | 待关口 B |
| c1 | 实现 | 建议去掉“匿名评论” | 挑战 | — | 和访问码权限冲突 | 保留 | 高 | 待关口 C |
```

- 编号：机械型用数字，口味型 `d1, d2…`，挑战型 `c1, c2…`，在整个需求里连续编号。
- “关口处理”列：关口过后写上结果，比如“关口 B 采纳”“关口 B 改为 B 方案”。
- 关口简报从这张表汇总；换会话时也从这里续上。

## 五、独立评审意见怎么处理

设计评审、代码评审都派一个**没看过过程**的子 agent 来做（同一个上下文自己审自己，盲区是一样的）。它的意见：

- 明确的错误、有清楚的改法 → 机械型，直接改。
- 有道理但可改可不改 → 口味型 `d<n>`，按你的判断定，列到关口。
- 要求改需求或范围 → 挑战型 `c<n>`。
- 你认为它错了 → 可以不采纳，但要在 `decisions.md` 里写一行理由。
