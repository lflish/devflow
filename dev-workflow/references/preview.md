# 用 vibeview 生成可看的页面

要让人看的东西，能用页面展示就不要只丢一段文字或本地路径：生成 HTML，上传 vibeview，给人链接。

## 能不能用

满足以下全部条件才用，否则退回 Markdown（见末尾）：
- 本机配置里 `preview.vibeview` 不是 `off`；
- `command -v dview` 能找到；
- 环境变量 `DVIEW_URL` 和 `DVIEW_TOKEN` 都有值。不要把 token 打印出来。

## 什么时候生成什么页面

| 时机 | 页面 | 源文件位置 | `--category` |
|------|------|------------|--------------|
| 关口 A（有界面、交互或流程时） | **效果页** | `pages/prototype/` | `prototype` |
| 每次机器关口放行、或有事等用户 | **汇总页**（一个需求一个，持续更新） | `pages/summary/` | `report` |
| 需求走不通、必须整体停下时 | **对比页** | `pages/compare-<n>/` | `doc` |

源文件都在需求文件夹下，见 layout.md。

## 上传

```bash
dview template match "<页面用途>" --json   # 先看有没有匹配的模板；有唯一匹配就按模板做
dview upload <需求文件夹>/pages/prototype/index.html --json \
  --category prototype --tag devflow --tag <需求短名> --model <当前模型 id> \
  -m "<这一版改了什么>"
```

- **同一个页面保持同一个链接**：在 git 仓库里，dview 会把“路径 → id”记在仓库根目录的 `.dview.json`。同一个路径再次上传，会成为同一链接下的新版本。所以源文件路径不要变，`.dview.json` 要提交。
- 多页面（效果页有好几个页面互相跳转）：把目录整个上传，`dview upload <目录> --json`，目录根要有 `index.html`，只用相对链接，单页应用用 hash 路由。
- 从返回的 JSON 里取 `url`、`accessCode`、`access.expiresAt`。**访问码和链接分开给人**，不要放进链接或页面里。
- 不要用 `--public`，除非人明确要求。

## 页面怎么写

- 默认单个自包含的 HTML 文件，不依赖外部资源。
- 浅色主题：背景 `#f6f8fb`，卡片白色，文字 `#1e293b`，强调色 `#2563eb`。项目有自己的设计风格时跟项目走。
- 手机宽度下也要能看：两侧留 16px，不能出现横向滚动。
- 结论放在最上面，细节往下放。

### 效果页（prototype）

- 目的是让人在确认需求前**看到做出来大概是什么样**，不是做真的产品。
- 用假数据，但要像真的：真实的字段名、合理的数量。
- 每个关键验收场景都能在页面上看到或点到：正常状态、空状态、出错状态、无权限状态。
- 页面顶部一行灰字：“效果示意，非最终实现”，并写上对应的需求名。
- 项目已有界面时，尽量模仿现有界面的样式，让人能对比改了哪里。

### 对比页（compare）

问题是什么（一两句）→ 每个方案一栏：做法、效果图或示意、优缺点、代价 → 推荐哪个、为什么 → 底部写“在终端回复 A / B / C”。

### 汇总页（summary）

内容和终端里的汇总一致（见 gates.md），多放：
- 最上面：等你的事（`c` 和 `d`），每条带推荐、依据、风险；
- 场景对照表：场景 → 怎么验证的 → 结果 → 截图（点开看大图）；
- 方案要点和结构示意图（机器关口 B 之后）；
- 验证结论：结论、验证者、对应提交；
- 历史：每次更新加一行时间和发生了什么，最新的在上面。

截图复制到页面同目录，按目录上传；或者转成 data URI 嵌进去（注意总大小不超过 1 MB 左右）。

## 不能用 vibeview 时

照样生成 HTML 文件，放在同样的位置，在简报里给出本地路径；同时在终端里把关键内容用 Markdown 讲清楚。流程不受影响。
