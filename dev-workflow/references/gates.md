# 关口：什么时候、给人看什么、怎么解析回复

关口是人集中投入注意力的地方。要让人几分钟内看完、做完决定：**结论放前面，每个要决定的事都带默认值，回复一个词就能通过。**

## 关口一览

| 关口 | 由谁发起 | 人看什么 | 页面 |
|------|----------|----------|------|
| 评审（需求评审消息） | dev-requirements | 理解、前提、做法、范围、问题 | 无 |
| **A 需求确认** | dev-requirements | 要做 / 不做、场景、假设、剩余问题 | 效果页（有界面或流程时） |
| **B 方案确认** | dev-plan | 方案、口味型和挑战型决定、任务、风险 | 方案简报页 |
| **AB 合并确认**（规模“小”） | dev-plan | A 和 B 的内容合在一起 | 效果页（有界面时） |
| **C 验收** | dev-accept | 场景结果和截图、决定、遗留问题、后续 | 验收页 |
| **D 对外动作** | dev-cicd | 合并、推送、PR、发布、部署的清单 | 无 |

## 发出简报时

1. 状态行写 `待关口：<关口>`，提交当前产物。
2. 在终端给出简报（下面的格式），有页面时链接放在第二行，访问码单独写，不放进链接。
3. 等人回复。**这一轮到此结束**，不要在等待时继续做别的阶段。

## 简报格式

### 关口 B / C（D 的格式见 dev-cicd）

```markdown
## 关口 B：方案确认 · <需求名>

**一句话**：<这次要做什么、用什么方案，一两句>
**页面**：<url>　访问码：<code>（<到期日期> 过期）
**紧急**：<安全或数据风险、阻塞的任务、没做的浏览器测试；没有就写“无”>

### 需要你决定
c1. <标题>
    你原来定的：…
    建议改为：…
    理由：…　　改错的代价：…
    默认：保持原样

### 已按推荐定下（可改）
d1. <标题>　默认 A：<…>　备选 B：<…>　（依据：原则 2）
d2. …

### 其他
- 自动决定 12 条，见 decisions.md
- 任务 9 个，预计改动 14 个文件
- 风险：…

回复 `all` 全部按默认通过；或 `d1 B`、`c1 同意`、`问 d2`、`重做 <原因>`。
```

### 关口 A / AB

```markdown
## 关口 A：需求确认 · <需求名>

**一句话**：<要做什么；选的做法；范围模式>
**效果页**：<url>　访问码：<code>（<到期日期> 过期）

**要做**：…（3–6 条要点）
**不做**：…
**推迟**：E2 …
**验收场景**：共 12 个，最重要的：R1.1 …；R2.3 …；R4.1 …

### 我做的假设（可改）
H1. 评论只支持纯文本（依据：项目里所有输入都按纯文本处理）
H2. …

### 还需要你回答（都有默认）
Q3. <问题>　默认 A：…　备选 B：…

### 其他
- 新建了 .devflow.yml，请看一下命令对不对
- （AB 时加上）技术方案：…；任务 4 个；d1 …

回复 `all` 全部按默认；或 `H2 改为 …`、`Q3 B`、`R2 去掉`、`问 H1`、`重做 <原因>`。
```

规则：
- 每次最多列 7 个 `d`；超过说明拆得太细，合并同类项。
- 挑战型 `c` 的默认值永远是“保持人原来定的”。
- 没有任何要决定的事时照样要过关口，简报只剩“一句话”和“其他”。

## 解析回复

| 回复 | 含义 |
|------|------|
| `all`、`通过`、`ok`、`可以`、`同意` | 全部按默认 |
| `d1 B`、`d1 改成 <…>` | 改这个口味型决定，其余按默认 |
| `c1 同意` / `c1 不同意` | 采纳或不采纳这条挑战 |
| `Q3 B`、`Q3 <简答>` | 回答这个问题 |
| `H2 改为 <…>`、`H2 不对` | 修改或推翻这条假设（推翻时按反面处理，拿不准就当作一个问题重新列出） |
| `P1 不同意：<…>` | 前提不成立，按人的说法重新梳理受影响的部分 |
| `E2 加入` / `E2 推迟` / `E2 不做` | 扩展候选的去向 |
| `选 B` | 产品做法选 B |
| `R2 去掉`、`R2.3 改为 <…>` | 删除或修改需求、场景 |
| `问 <编号>` 或任何提问 | 先回答，再重新给出简报（只列有变化的部分），不算通过 |
| `重做 <原因>` | 回到这个阶段的开头，按原因修改 |
| 多项用逗号或换行隔开 | 逐项处理，没提到的按默认 |
| 看不懂的回复 | 不要猜。说明哪部分没看懂，重新给出简报 |

## 有改动时

1. 修改受影响的产物（spec、design、tasks、代码），在 decisions.md 的“关口处理”列写上结果。
2. 重跑受影响的阶段：
   - 关口 A/AB：改了需求或场景 → 更新 spec 和效果页（同一链接的新版本）。
   - 关口 B：改了方案 → 重跑 dev-design 的工程评审和 dev-plan。
   - 关口 C：要改代码时，在 tasks.md 加“返工”任务（状态“待办”，写明来源，比如“关口 C：d2 改为 B”），状态改回“实现中”，阶段改为 dev-implement，然后依次走实现 → 测试 → 评审 → 验收。
3. 重新给出简报，只列有变化的部分。
4. 同一个关口最多来回 3 轮。第 3 轮后还没通过，建议回到上一个阶段重新梳理。

## 关口通过后

1. decisions.md 每个 `d`/`c` 的“关口处理”列补全。
2. 状态行：改“状态”（见 layout.md），清空“待关口”，“阶段”改成下一阶段；同步索引。
3. spec 的“变更记录”写一句：关口 X 通过，改了什么。
4. 提交。
5. **在同一轮里立刻读下一阶段的 SKILL.md 并执行**，不要再问。
