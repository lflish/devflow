# 机器验证：怎样才算可信

机器关口 B（设计）、C（测试）和合并，放行的唯一依据是**验证结论**。CI 全绿、写代码的 agent 说“做完了”都不算。借鉴 pstack 的 autopilot / shipping / interrogate。

## 六条规则

1. **验证者没写过这段代码。** 每次派全新的验证者，不复用做过开发的上下文。
2. **在真实环境里跑。** 重跑测试和 lint；有界面的，用测试浏览器把每个关键场景像用户一样走一遍（按项目的 `verify-<项目名>` skill 操作）。只读代码、只跑单元测试不算。
3. **问题要有运行证据。** 每个问题附上：执行的命令或操作、实际输出、按 spec 应有的结果。跑不出来的不算问题。
4. **结论绑定代码。** 结论记下验证时的提交 sha 和**代码指纹**（见下）。之后：
   - 只有需求文件夹、`.dview.json` 变了（写结论、汇总、状态）→ 指纹不变，结论仍有效，**不复验**；
   - 指纹变了，或默认分支的**代码**前移后做过变基、合并、解决冲突（判断方法见下面“代码指纹”）→ 复验：只是修复、变基、冲突处理的，派**一个**验证者；新功能、重新设计、改了 5 个以上文件或改了接口的，重跑**全套**。
5. **只拦用户会遇到的问题。** 能拦下的：功能和 spec 不符、检查没通过、文档写错、安全或数据风险。其余记进后续，不拦。
6. **放松检查一律交给人。** 验证者发现测试被删、断言被放宽、超时被调大、加了忽略规则，记 `c<n>`，结论里单列，这一项不放行。

### 代码指纹

只算代码，不算需求文件夹和 `.dview.json`：

```bash
BASE=$(git merge-base <默认分支> <sha>)
git diff "$BASE" <sha> -- . ':(exclude)<docs_dir>' ':(exclude).dview.json' | git patch-id --stable | cut -d' ' -f1
```

把结果写进结论的“代码指纹”一行。比较时对当前提交用同一条命令算一遍。同时检查 `BASE` 有没有变。变了（默认分支前移并变基过）时，看新旧 BASE 之间的**代码**改动：

```bash
git diff --stat <旧 BASE> <新 BASE> -- . ':(exclude)<docs_dir>' ':(exclude).dview.json'
```

为空（默认分支只多了文档或状态提交）→ 不复验；不为空 → 按规则 4 复验，即使指纹相同。

## 验证者用哪个模型

优先用**同级别的其他模型**（不同模型的盲区不同），没有再用同一个模型开一个全新的子 agent。

本机配置 `verify.models` 按顺序列出候选（默认 `[codex, claude, same]`），逐个尝试：

1. 跳过当前工具自己对应的那一项（在 Claude Code 里跳过 `claude`，在 Codex 里跳过 `codex`），因为那就是写代码的模型。
2. 其余每个候选先**探测**，限时 `verify.probe_timeout`（默认 60 秒）：
   - `codex` / `codex:<模型>`：`timeout 60 codex exec [-m <模型>] --skip-git-repo-check "只回复 OK" < /dev/null`
   - `claude` / `claude:<模型>`：`timeout 60 claude -p "只回复 OK" [--model <模型>] < /dev/null`
   - `agent:<模型>`、`same`：不用探测。
   输出里没有 OK、超时、报错都算不可用。同一轮验证里探测结果复用。
3. 第一个可用的就是验证者。
4. 都不可用，或当前工具没有子 agent（比如 Codex 没开 spawn_agent）：在当前上下文里按提示词自己验证，结论里写“验证由同一上下文完成”；这次**不能**自动放行，L2/L3 也改为按 L1 请用户看一眼。
5. 结论里写明用了谁、为什么（例如“验证者：claude 全新子 agent；codex 不可用：探测 60 秒超时”）。

“同级别”由用户在 `verify.models` 里指定的模型保证（例如 `codex:gpt-5.4-pro`）；不写模型就用那个工具自己的默认配置。

## 怎么调用

外部模型的验证者在**独立的 worktree** 里工作，不碰开发用的目录：

```bash
WT=.devflow-tmp/verify-<短 sha>
git worktree add --detach "$WT" <sha>
(cd "$WT" && <commands.install>)
```

然后按候选类型调用，**一律在后台运行**（Claude Code 用 Bash 的后台运行，等完成通知；不要在前台等，前台有时间上限），限时 `verify.run_timeout`（默认 1800 秒）：

| 候选 | 命令 |
|------|------|
| `codex[:<模型>]` | `timeout 1800 codex exec -C "$WT" [-m <模型>] --sandbox workspace-write -c sandbox_workspace_write.network_access=true --add-dir <需求文件夹绝对路径> --skip-git-repo-check "<提示词>" < /dev/null` |
| `claude[:<模型>]` | `cd "$WT" && timeout 1800 claude -p "<提示词>" [--model <模型>] --add-dir <需求文件夹绝对路径> --allowedTools Read Grep Glob Write Edit Bash < /dev/null`（提示词放最前面：`--add-dir`、`--allowedTools` 会吞掉后面所有参数） |
| `agent:<模型>` | 当前工具的子 agent，指定模型（例如 Claude Code 的 Agent 工具 `model: fable`），提示词里写明在 `$WT` 下工作 |
| `same` | 当前模型的全新子 agent，同上 |

- 网络：codex 的沙箱默认断网，上面的 `network_access=true` 让它能连测试浏览器和被测环境。
- 权限：claude 只开放上面列的工具，**不要**用跳过全部权限确认的模式；验证者需要的只是读代码、跑命令、写结论和截图。
- 结论和截图写到需求文件夹（已用 `--add-dir` 授权），不要写进 worktree 里的代码。
- 外部验证者可能没有浏览器 MCP：它运行项目里的 Playwright 测试和临时脚本连测试浏览器（环境变量 `DEVFLOW_BROWSER_CDP` 会被继承）。连浏览器也做不到时，界面场景由 `same` 验证者补跑，结论里分开写。
- 验证结束后 `git worktree remove --force "$WT"`。

## 验证者的提示词

```
你是独立验证者。你没写过这段代码，你的任务是证明它对不对，而不是解释它。

需求：<spec.md 绝对路径>（重点看“需求与验收场景”和“完成条件”）
设计：<design.md 绝对路径，没有写“无”>
任务和测试计划：<tasks.md 绝对路径>
要验证的提交：<sha>，代码在 <worktree 绝对路径>（只在这里运行，不要修改代码）
环境：<verify_env 的名字和地址>，数据规则：<该环境的 data 规则>
项目验证方法：<verify-<项目名> skill 的路径，没有写“无”>
浏览器：环境变量 DEVFLOW_BROWSER_CDP（没有就用本机无头浏览器）

请做：
1. 按项目命令重跑 lint 和全部测试，以及 `.devflow.yml` `invariants` 里每条规则的检查命令，记录命令和结果。
2. 按“需求与验收场景”逐个验证：能自动化的跑对应测试；有界面的用浏览器像用户一样走一遍，截图存到 <evidence 目录绝对路径>。检查“完成条件”是否成立。
3. 读 diff（git diff <基准>...<sha>），找 spec 没写到但用户会遇到的问题；检查有没有测试被删、断言被放宽、超时被调大、加了忽略规则。
4. 每个问题必须附：命令或操作、实际输出、应有结果。跑不出来的不要写。

把结论写到 <verdict 文件绝对路径>，格式：
- 结论：通过 / 通过，有备注 / 不通过
- 提交：<sha>　代码指纹：<按 verification.md 的命令算>
- 验证者：<你是谁>
- 检查：每条命令和结果
- 场景：每个场景 → 怎么验证的 → 结果 → 截图
- 完成条件：成立 / 不成立，依据
- 问题：每条带证据、严重程度、是否拦（只有用户会遇到的才拦）
- 放松检查：发现的每一处（没有写“无”）
```

## 结论怎么用

派验证者之前，把上一轮的 `verdict.md`（如果有）追加到 `verdict-history.md` 末尾，再开始新一轮。

| 结论 | 下一步 |
|------|--------|
| **通过** | 机器关口放行，写进汇总 |
| **通过，有备注** | 放行；备注进 tasks.md 的“后续”和汇总 |
| **不通过** | 回到开发：每个拦下的问题变成一个“返工”任务（先写复现它的测试）；修完按规则 4 重新验证。同一个问题 3 轮仍不通过，按 gates.md 记 `c<n>` 并等用户 |

有放松检查或其他未决 `c<n>` 时：结论可以是“通过，有备注”，但这些项保持暂停，汇总里列在最前面；**这样的需求不能合并**（见 dev-release）。

结论文件：机器关口 B 写进 `design.md` 末尾的“方案验证”一节；机器关口 C 写到需求文件夹的 `verdict.md`。
