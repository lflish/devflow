# 需求评审：先确认做的是对的东西

借鉴 gstack 的 office-hours 和 plan-ceo-review。目的不是“把人说的写下来”，而是在动手前确认：**问题找对了、范围合适、方向对**。
所有结论都放进第 4 步那**一条**评审消息里，不要一项一项地问。

## 1. 先判断是哪类需求

从人的描述和项目本身判断，不用专门问（实在看不出来时，作为评审消息里的一个问题）：

| 类型 | 姿态 |
|------|------|
| 面向用户的产品、商业项目 | 严格：追问真实需求、现在怎么解决、最小可交付版本 |
| 公司内部工具 | 务实：最快交付价值的版本，谁会用、用来干什么 |
| 个人项目、学习、探索、演示 | 帮忙把想法做到最有意思：最酷的版本、最快能给人看的版本 |
| 修 bug、重构、改配置 | 保持范围：找到最小改动，守住现有行为 |

## 2. 前提挑战

在提方案之前，先回答这几个问题（自己先查代码和文档回答）：

1. **问题找对了吗？** 换一个角度看，有没有简单得多、或价值大得多的做法？
2. **什么都不做会怎样？** 痛点是真实发生过的（谁、多频繁、代价多大），还是设想出来的？
3. **现有代码已经解决了多少？** 列出能复用的模块、工具、流程。要重写已有功能时，说明为什么改造现有的更差。
4. **交付物怎么到用户手里？** 新的命令行工具、库、镜像、应用，要写明发布渠道；或者明确说这次不管发布。

把结论写成 2–4 句**前提**，让人逐条同意或不同意：

```
前提（不同意的请指出）：
P1. 现在评审靠截图发群里，意见散在聊天记录里，找不回来——这是要解决的问题。
P2. 评论只需要对应页面的某个版本，不需要精确到页面上的某个位置。
P3. 已有的访问码机制可以直接用来控制谁能评论。
```

## 3. 说法含糊时，直接给出你的理解

人说的是“更好的协作”“智能一点”“体验流畅”这种词时，不要只问“你指什么”，而是**建设性地改写**：

> 我理解你实际要的是：评审人打开预览链接就能直接在页面旁边留言，作者在一个地方看到全部意见并逐条标记处理。是这样吗？

区分真实的和设想的：“我觉得用户会想要……”是设想；“上周三个人都把意见发错了群”是真实的。设想的需求，范围要更保守。

## 4. 产品层面的做法（有明显不同的做法时）

这里说的是**做成什么样**，不是技术实现（技术方案在 dev-design）。列 2–3 个：

```
方案 A：最小可行 — 只在页面底部加评论列表
  工作量：小　风险：低　复用：访问码、版本
  好处：…　坏处：…
方案 B：理想形态 — 页面上框选位置批注 + 处理状态 + 确认签字
  工作量：大　风险：中　…
方案 C：换个思路 — 不做评论，接入已有的 issue 系统
  …
推荐 A，因为：…
```

规则：必须有一个“最小可行”（改动最少、最快交付）；可以有一个“理想形态”；有真正不同的思路时再加“换个思路”。只有一种合理做法时不用列。

## 5. 范围模式

按下面的规则推荐一种（第一个符合的生效）：

| 情况 | 推荐模式 | 含义 |
|------|----------|------|
| 全新的产品或系统 | **扩展** | 想想 10 倍好的版本是什么样，列出扩展让人挑；核心范围仍以“最小可行”为准 |
| 修 bug、重构 | **保持** | 不加不减，把边界、出错路径、测试做扎实 |
| 给已有产品加功能，预计改动超过 15 个文件 | **缩减** | 找出最小核心，其余推迟 |
| 给已有产品加功能 | **选择性扩展** | 守住核心范围，另外列出几个值得考虑的扩展，让人挑 |

扩展候选最多 5 个，每个写清：用户能感受到什么、工作量（小/中/大）、风险。每个让人选：

- **加入**：进入本次范围
- **推迟**：记进“后续”，不做
- **不做**：写进“不做”，附理由

默认值：选择性扩展和扩展模式下，工作量“小”且风险低的推荐加入，其余推荐推迟。**扩展只能由人选择加入，绝不悄悄加进范围。**

“缩减”和“保持”模式下，如果建议把人原本要的东西推迟，也要逐项列出、让人选“推迟 / 保留”，默认保留。

## 6. 理想状态对照（标准规模）

```
现状                    本次                         一年后的理想
评审意见散在群里   →    预览页上直接评论、可确认    →   需求评审全流程在 vibeview 里完成
```

确认本次是朝着理想走的，而不是走到一条以后要推翻的岔路上。如果是岔路，作为一个前提或问题提出来。

## 7. 评审消息的结构

第 4 步（dev-requirements）发出的那一条消息，按这个顺序组织，可以省略不需要的部分：

```markdown
## 需求评审 · <需求名>

**我的理解**：<改写后的需求，≤200 字：要什么、给谁、为什么、现在是怎样>

**前提**（不同意的请指出）
P1. …
P2. …

**做法**（产品层面）
A. 最小可行：…（推荐）
B. 理想形态：…

**范围**：推荐“选择性扩展”。可选的扩展：
E1. <用户能感受到什么>　工作量小　→ 推荐加入
E2. …　工作量大　→ 推荐推迟

**问题**
Q1. …（格式见 questions.md）

回复 `all` 全部按推荐；或 `P2 不同意：…`、`选 B`、`E2 加入`、`Q1 B`。
```

前提最多 4 条，扩展最多 5 个，问题最多 5 个。所有部分加起来要让人 3 分钟内看完。
