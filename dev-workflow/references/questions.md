# 怎么问人问题

什么时候可以问人，以 decisions.md 的“停止情况”和“允许问人的例外”为准。这里只讲问题怎么写。关口简报的格式见 gates.md。

## 问之前

- **先查后问**：代码、文档、已有的 spec、git 记录能回答的，一律不问。
- **能猜就猜**：有合理默认值的（行业惯例、项目惯例），自己定，写进 spec 的“假设”，在关口 A 列给人看。
- **只问会改变结果的**：答案不同，要做的东西或验收方式就不同。措辞、样式偏好这类不问。
- **需求阶段不问实现方法**：用什么库、怎么拆模块，是 AI 的事。

## 一次问完

把所有问题放在**一条消息**里，按“影响 × 不确定性”从高到低排，最多 5 题（规模“小”最多 3 题）。
默认用文字消息列出问题，方便人在一行里回答多题；不要用弹窗一题一题地问。

## 每个问题的格式

```markdown
**Q2. 评论要按页面版本分开吗？**
为什么问：页面更新后，旧评论可能对不上新内容；这决定数据怎么存、界面怎么显示。
推荐 A：按版本分开，旧版本的评论在版本历史里还能看到。
- A. 按版本分开（推荐）
- B. 所有版本共用一组评论
- C. 其他（一句话说明）
```

- 问题本身要是一个完整的问句，不能只写一个标签（比如“版本策略”）。
- “为什么问”一句话，说清答案会改变什么。
- 推荐项放在最前面，写清理由。
- 选项 2–4 个，互斥。只能简答时写“建议答案：…”。

消息结尾写：

```
回复 `all` 全部按推荐；或逐题回答，如 `Q2 B，Q4 只要管理员能删`。
```

## 收到回答后

- `all` 或“按推荐”：全部采纳推荐项。
- 部分回答：没回答的按推荐处理，在“假设”里标注“未回复，按推荐”。
- 回答引出了新的关键问题：按推荐定、写进假设，到关口 A 一起确认。只有人不同意某个前提、而且影响大时，才允许再追问一轮（见 decisions.md 的例外 2）。
- 每个答案马上写回 spec 的“问答记录”，并更新正文里对应的地方。
