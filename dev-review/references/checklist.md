# 评审清单

分两轮。第一轮是会让产品出错的问题，第二轮是其他问题。只报告真问题，每条定位到 `文件:行号`，给出改法。

## 第一轮：严重（会测试失败、线上出错、丢数据或泄露）

### 需求和设计一致性
- 每条需求、每个场景都实现了吗？行为和 spec 写的一致吗（具体数值、文案、权限）？
- 接口签名、数据字段和设计一致吗？不一致时，是设计漏了还是实现错了？
- 有没有做了 spec 没要求的事？

### 数据安全
- SQL、命令、模板是否拼接了外部输入（必须参数化或转义）
- 先查再写的竞态（查到不存在再插入，没有唯一约束兜底）
- 状态变更不是原子的（并发时会跳过或重复）
- 绕过校验直接写数据库
- 删除或覆盖数据前没有确认、没有备份

### 并发
- 读-判断-写没有锁或唯一约束
- 重复提交（连点、重试）会产生重复数据
- 共享资源（文件、连接、全局变量）的竞争

### 新取值是否处理完整
新增了枚举值、状态、类型、或放宽了输入（新的文件类型、新参数）时：
- 搜出**所有**用到同类值的地方，逐个读（不只是搜），确认每处都处理了新值。常见遗漏：前端加了选项，后端没存；`switch` 落进了错误的默认分支。
- 这一步要读 diff 以外的代码。

### 不可信输入
- 用户输入、页面内容、外部接口返回、大模型输出，在写库、拼命令、渲染 HTML、请求 URL 之前有没有校验
- 把用户内容当 HTML 插入页面（XSS）
- 按外部给的 URL 发请求，没有限制目标（SSRF）

### 安全
- 代码里有真实的密码、token、密钥
- 接口有没有认证和权限校验；调试接口在生产环境是否关闭
- 新依赖有没有已知漏洞（有 lock 文件就跑 `npm audit` / `pip-audit` 之类的工具）

### 外部影响和不变规则
- 新增的发消息、扣费、推送、调用付费服务，有没有默认关闭的开关（只有设成 true 才打开）
- 测试有没有访问真实的外部服务或付费服务（应该只连本地假服务）
- 项目 `invariants` 的检查命令都还能通过；这次新增的规则有没有配检查
- 数据库迁移（有数据库的项目）：已经发布的迁移没被修改；新迁移能在线执行，不长时间锁表；大批量数据改动不放进迁移；破坏性变更有升级和回退说明

### 检查是否被放松
检查是任何能让这次改动失败的东西：测试、断言、阈值、超时、lint 规则、类型检查、CI 步骤、快照。逐个看 diff 里改到这些东西的地方，问一个问题：
**这个放松是为了让本该报出的失败消失，还是有 diff 里能看到的理由（测量数据、spec 改动）？**
- 删除或跳过测试、断言变弱、快照随便更新、超时调大、加忽略注释、吞掉异常
- 测试不可能失败：断言的是自己准备的数据、和实现一模一样地重算一遍、没有反面情况
- 这一类问题**一律不自动处理**，记为 `c<n>` 交给用户

## 第二轮：一般

### 正确性和边界
- 差一错误、空值、零、溢出、时区、编码
- 错误路径：外部调用失败、超时、重试有没有上限和退避
- 资源（文件、连接、锁）在出错时是否释放
- 错误被静默吞掉；错误信息对排查有用、但不对用户泄露内部细节

### 测试
- 每个场景有测试吗？测试真的断言了预期行为，而不是“没报错就算过”？
- 测试守行为不守写法：不断言私有常量、CSS 类名、像素位置，不把重构前的输出钉死；复现问题的测试并进这个功能已有的测试文件
- 边界和异常有测试吗？

### 改全
- 新的环境变量写进了 `.env.example`（或项目的同类文件）
- 改了配置的含义，示例配置、文档跟着改了；已部署的环境升级时要做的事写进了 `upgrade_doc`（没配就看 design.md“变更”里标“升级步骤”的内容，小规模看 tasks.md“技术方案”里的）
- 改了一个名字或入口，所有出现它的地方都改了
- 停用一个功能时，它的代码、测试、文档、定时任务、配置项一起删了；数据库表和字段的删除是难以回头的决定，按 decisions.md 记 `c<n>`，写好迁移和回退说明

### 可维护性
- 命名清晰、和项目一致
- 重复代码；项目里已有的函数被重写了一遍
- 过长的函数（超过 80 行）、过深的嵌套
- 魔法数字和字符串
- 过时的注释；需求之外的抽象和配置项（为“以后可能用到”而写的）
- 没有证据的防御代码：加锁、重试、兼容旧格式、开关、兜底，要能说出真实发生过的情况或平台机制

### 文档
- 改了行为，README、使用说明、接口文档是否同步更新
