# dev-implement：实现

目标：**把计划连续做完，中途不打扰人。**
人已经在关口 B 同意了计划。执行中的冲突、歧义、计划漏洞都由你裁决、记录，然后继续。

## 开始

1. 先读 `../dev-workflow/SKILL.md` 的“每次开始时”并照做（包括读 `../dev-workflow/references/decisions.md`）。
2. 前提：spec 状态是“实现中”（关口 B/AB 已通过，或关口 C 打回返工）。状态是“草案”“已确认”的，说明计划还没确认，回到 dev-plan。
3. 状态行“阶段”改为 `dev-implement`。
4. 确认在 `change/<短名>` 分支上（dev-requirements 已建；没有就新建）。
5. **独立模式**：没有需求文件夹、用户只是让你写一段代码时，照常写代码和测试，不读写 tasks.md，不交接。

**接着做**：读 tasks.md 的“进度”和 decisions.md 最后几行，从第一个“进行中”或“待办”的任务继续。

## 1. 每个任务

1. **选任务**：第一个“待办”、且依赖都已完成的任务（“进行中”的优先，说明上次没做完）。把它改成“进行中”。
2. **读上下文**：任务描述、接口、对应场景；design.md 相关部分；要改的文件和周围的代码。
3. **先写测试**：按任务里列的单元、集成测试名和断言写。浏览器层的测试不在这里写（由 dev-test 写），但要按任务要求加好 `data-testid`。
4. **运行，确认它失败**，而且是因为功能还没实现而失败，不是因为测试写错、导入错误。
5. **实现**：写让测试通过的最少代码。遵循项目惯例和 `.devflow.yml` 的 `rules.implement`。
6. **运行这个任务的测试**，然后运行相关的全部测试，确认没有破坏别的东西。
7. **按完成定义验证**：运行完成定义里的命令，核对输出。
8. **提交**：只提交这个任务的改动，提交信息用约定格式（`feat:` `fix:` `refactor:` `test:` `docs:` `chore:`），说明做了什么。
9. **记录**：任务状态改为“完成”，在“进度”表追加一行（时间、提交、测试结果）。和提交同时做，不要攒到最后。

然后马上做下一个任务。**任务之间不停顿、不汇报进度、不问“要继续吗”。**

## 2. 遇到问题时：裁决，不停等

| 遇到 | 怎么做 |
|------|--------|
| 计划里的接口不合理、漏了一步 | 按决策原则改，记一行（机械型或口味型）；影响后面任务的，同步改 tasks.md |
| 设计和实际代码对不上 | 以 spec 为准调整做法，在 design.md 的“变更”里写一行，decisions.md 记一行 |
| spec 有歧义 | 选最符合 spec 目的的理解，记为口味型 `d<n>` |
| 觉得需求本身该改 | 按原需求做，记挑战型 `c<n>` |
| 发现范围外的改进机会 | 记进 tasks.md 的“后续”，不做 |
| 测试失败 | 先查测试是否写错，再查实现，最后查设计。修实现，不改测试迁就实现 |
| 同一个问题试了 3 次还不行 | 任务状态改为“阻塞”，写一行阻塞原因（现象、试过什么），先做不依赖它的任务；依赖它的任务也标“阻塞”。到关口 C 列进“紧急” |

**只有这 4 种情况可以停下来问人**（详见 decisions.md）：不可逆的操作、安全敏感的操作、对外的副作用（推送、发布、部署）、spec 根本走不通。

## 3. 全部完成后

“没有待办、也没有进行中”的任务时（剩下的都是“完成”或“阻塞”）：
- 运行全部测试和 lint（`.devflow.yml` 的 `commands`），附上输出。
- 确认没有未提交的改动。
- 阶段改为 `dev-test`，然后读 `../dev-test/SKILL.md` 并执行。

## 不要做的事

- 不要一次做多个任务，也不要提前做后面任务的事。
- 不要做重构，也不要改任务范围以外的文件（决策原则 4 允许的补全除外）。
- 不要留指向本该在当前任务完成的 `TODO`。
- 不要删测试、跳过测试、放宽断言、调大超时、加忽略规则来让检查通过。确实需要时，记挑战型 `c<n>`。
- 不要改任务的完成定义来迁就实现。
- 不要推送到远程：推送属于对外动作，攒到关口 D。
