# dev-release：发布

目标：**合并受验证结论和目标分支保护约束，上生产按明确范围确认。** 项目有自己的发布或部署 skill 时，具体操作交给它，本 skill 只负责前后的检查和确认。

## 开始

1. 先读 `../dev-workflow/SKILL.md` 的“每次开始时”，照做其中第 1–3 步（包括读 `../dev-workflow/references/decisions.md`、`verification.md`）。本阶段还要读同目录下的 `gates.md`。
2. 有当前需求时，状态行“阶段”改为 `dev-release`；状态应为“已验证”（机器关口 C 已放行）或“已合并”（上生产这一步）。
3. **独立模式**：没有需求文件夹（用户只是要“搭个 CI”“发个版”）时，不读写需求文件。项目有自己的发布 skill 时交给它执行，合并和生产影响仍按本阶段的规则检查。没有有效的验证结论时交给用户处理合并。
4. **记数据**（metrics.md）：阶段开始、结束；复验派验证者后记“用量”；合并前复验的结论；合并、上线各记一行（合并后的这些行随写回一起提交）。

**接着做**：读 spec 变更记录和本地 `devflow-writeback/*` 中的待写回记录，按 PR 或本地目标 ref、发布记录和实际部署版本核对已执行动作。默认分支上的 spec 落后时，用已确认的实际结果恢复进度。动作结果仍不明确时先查明，不重试可能已完成的发布或部署。

## 1. 了解现状

- `.devflow.yml` 的 `commands`、`release`、`environments`。
- 已有的 CI（`.github/workflows/`、`.gitlab-ci.yml`、`Jenkinsfile` 等）、发布和部署方式（脚本、Dockerfile、项目自己的发布 skill）。
- 按 [decisions.md 的“默认分支更新的生产影响”](../dev-workflow/references/decisions.md#默认分支更新的生产影响) 检查推分支、开 PR、合并和默认分支写回的实际触发条件。合并会触发生产时纳入第 4 步，影响不明时保持等待。
- 分支和远程：当前分支、默认分支、`git remote -v`、能不能用 `gh` 等平台命令。

**已有的东西优先沿用和补充，不要覆盖。**

## 2. CI（没有或不完整时才做）

CI 跑的和本地一样：安装 → lint → 测试 → 构建 → 浏览器测试，任何一步失败就停。
- 命令全部用 `.devflow.yml` 的 `commands`。
- 浏览器测试在 CI 里用本机无头浏览器：不设 `DEVFLOW_BROWSER_CDP`，测试会自动改用本机浏览器；用 Playwright 的 `webServer` 启动被测服务；先 `npx playwright install --with-deps chromium`。
- 构建完把产物真正启动起来做冒烟检查（打开首页、调一个健康检查接口），不只跑单元测试；任何一步失败都打印服务日志的最后几十行。
- 失败时上传截图和 trace。
- CI 里 `safety_valves` 全部关闭，不访问真实的外部服务和付费服务。
- 密钥只用 CI 平台的 secrets，在 `docs/secrets-checklist.md` 列变量名和用途（不写值）。
- **不要加“合并就自动部署生产”的步骤**；部署生产始终走第 4 步的确认。

没有任何现成方式时，参考 [references/github-docker-example.md](references/github-docker-example.md)（示意，不能直接用）。改完先在本地按顺序跑一遍。CI 改动是验证之后加的：按 verification.md 规则 4 复验一次（指纹会变），并在汇总里列出。

## 3. 推送、开 PR、合并

**合并的前提**（任何一条不满足就不合并，停在“已验证”，写进汇总的“等你决定”）：
- tasks.md 里没有“阻塞”的任务；
- 没有未决的 `c<n>`（包括放松检查）；
- 验证结论是“通过”或“通过，有备注”。

步骤：
1. 确认推送分支和开 PR 都不会触发生产后，推送 `change/<短名>` 并开 PR 到默认分支。任一动作会触发生产或影响不明时按 decisions.md 的生产影响规则处理。标题用约定格式，正文固定三段：
   - **解决什么问题**：目标、完成条件，关联的 Issue；
   - **怎么验证的**：实际跑过的检查和结果、验证结论和验证者、汇总页链接；**没跑的检查写明原因**；页面改动附截图；
   - **兼容与使用影响**：配置、数据库迁移、公开接口、升级步骤（同时写进 `upgrade_doc`；没配 `upgrade_doc` 就只写在这里）；没有就写“无”。
   没有远程仓库时跳过 PR，按第 3、4 小步检查并执行本地合并。
   **推送前先 `git fetch`，看默认分支有没有被改写**（远程默认分支不包含本地默认分支的提交，`git merge-base` 退到很早以前）：
   - 先确认本地默认分支没有远程缺少的内容（和远程对应的提交 `git diff` 为空）；不为空就停下，把差异写进汇总，记 `c<n>` 等用户；
   - 先建新分支再搬：`git branch change/<短名>-2 change/<短名>`，`git rebase --onto origin/<默认分支> <本地默认分支> change/<短名>-2`，旧分支保持原样；开新 PR，关掉旧 PR 并说明原因；在 spec 变更记录里写一句“之后用分支 change/<短名>-2”；**不要强推**旧分支，也不要把两段历史合并（共同祖先太早，会出现大量假冲突）；
   - 按下文第 3 小步检查新分支，必要时复验；
   - 本地默认分支要对齐远程（`git reset --hard origin/<默认分支>`）时不要自己做：有上生产清单就放进清单；没有（项目没配发布和部署）就写进汇总的“等你决定”，注明“不影响合并”（不记 `c<n>`，否则会挡住合并）。
2. 用 `gh pr checks --watch`（或对应平台的命令）等 CI。无远程时在候选上运行第 2 步的项目检查。CI 失败：按 dev-build 的做法修复、提交，有远程时再推送；同一个问题失败 3 次就停下报告用户。
3. **检查结论还覆盖要合并的代码**：获取平台上 PR 当前的 head 和目标分支当前 tip，解析成准确 SHA。本地合并用对应分支的当前 SHA。取 `verdict.md` 中 `- 验证快照：` 后面的一行 JSON 作为 `$SNAPSHOT`，用 `python3 <dev-workflow>/scripts/verification_snapshot.py check --repo <仓库> --docs-dir <docs_dir> --head <head SHA> --target <目标 tip SHA> --snapshot "$SNAPSHOT"` 校验。比较完整的候选代码树和目标分支代码树，成功后取输出的 `head` 作为合并条件。验证快照缺失、格式旧、命令失败或任一代码树变化时，先把当前目标分支集成进待验证 head（按项目惯例合并或变基，禁止未经授权强推），再按 verification.md 复验，更新结论并重新检查。仅凭 CI 通过不能替代结论。
   - 需求、验收场景、测试计划或验证方法有变时，即使快照校验通过，也按 verification.md 规则 4 对受影响范围复验。
   - 直接合并时，确认 PR 已集成当前目标分支，确保候选合并结果的代码树与已验证的代码树一致。若由合并队列合成候选，必须在队列上对实际候选校验 DevFlow 证据并运行必需的集成检查。目标基线变化后，相应的检查必须失效并重新验证。
   - 核对必需 CI 的通过结果确实对应本次校验输出的 head 或平台实际生成的合并候选。结果属于旧提交、候选不匹配或检查仍在运行时，回到第 2 小步等当前候选的必需检查。
   - 自动合并前，确认平台确实原子地约束已检查的 head 和目标基线，或者用强制合并队列保证上述验证对应最终合并候选。分支保护的名称、最后一刻 fetch、单独的 head 锁都无法证明目标基线受保护。
4. **合并**：
   - 合并会触发生产的，放到第 4 步明确确认。影响不明时保持等待。
   - 有远程但平台无法保证第 3 小步的原子条件时，所有等级都保留 PR 和验证证据，说明目标分支仍可能前移并交给用户处理合并。
   - **L1**：发汇总请用户确认合并，状态行写 `待关口：合并`，这一轮结束。收到回复后重新执行第 3 小步，确认批准仍覆盖当前候选。
   - **L2 / L3**：第 3 小步和生产影响检查均满足时，可以合并。
   - 所有等级在实际合并前复查生产影响。GitHub 用 `gh pr merge <PR> --match-head-commit <本次通过检查的 head SHA>`，直接合并时再按项目惯例选择策略（如 `--squash`），队列用平台要求的方式。其他平台用等价的 head 条件。不得绕过保护或队列。平台拒绝或候选变化时返回第 3 小步。
   - **无远程时**：使用第 3 小步校验输出的准确 `head` 和 `target`，确认 `git merge-base --is-ancestor <target SHA> <head SHA>` 成功、相关用户和生产授权满足。仅能在确保操作期间没有其他进程检出目标分支，且 `git worktree list --porcelain` 确认目标分支当前未被任何 worktree 检出时，执行 `git update-ref refs/heads/<默认分支> <head SHA> <target SHA>`，并读回目标 ref。目标 ref 并发变化时，Git 会拒绝更新，重新检查。条件不满足时，保留候选本地分支和证据，在 spec 和汇总里记录候选分支、目标和“待本地合并”，交给用户处理。
   合并后读回 PR 状态，确认真的合并了（进了合并队列或开了自动合并都不算）。
5. **写回状态**：按 [decisions.md 的“写回默认分支”](../dev-workflow/references/decisions.md#写回默认分支) 处理状态“已合并”、变更记录、索引和 metrics.md 里的合并记录。写回被拦下时在汇总里分别报告“已合并”和“待写回”，保留待写回提交。合并批准只覆盖已列明的合并动作。

**L3 一批需求**：每个需求只做到这一步（已合并；合并会自动部署生产的，停在“已验证”），全部需求都到了这一步后，再出**一份**合并的上生产清单（包括那些待合并的 PR）。

## 4. 上生产：一次确认

`release` 里没配发布和部署、合并也确认不会触发生产的，结束发布阶段：变更记录写“不上生产”，阶段清空，按第 3 步第 5 小步写回最终状态。合并的生产影响不明时保持等待。

把已明确范围的生产动作列成一份清单请用户确认（适用所有自主等级）。后来新增、变更的生产动作另行确认，包括会触发生产的状态写回：

```markdown
## 上生产确认 · <需求名，或这一批的需求列表>

**一句话**：发布 1.4.5 并部署到生产
要执行的动作：
1. （只在合并会触发生产时）合并（PR 或本地）—— 列明 PR 或本地候选及目标分支，说明触发的生产部署
2. 发布 1.4.5（按 release.publish：使用 $release 发布 1.4.5）
3. 部署到生产（按 release.production：使用 $deploy-view 部署 v1.4.5）
4. 上线后检查：读部署记录确认运行的是 1.4.5，打开首页截图；看部署之后的错误日志有没有新增（都是只读）
回滚方式：…

回复 `all` 执行全部；或 `只到 1`、`跳过`（不上生产，停在已合并）。
```

- 版本号按 `release.bump` 升（默认补丁号），`{version}` 是版本号，`{tag}` 是 `release.tag_prefix` + 版本号。
- 状态行写 `待关口：上生产`，**这一轮结束，等用户回复**。这一步只认 `all` 或明确的动作编号；“继续”不算确认。

## 5. 执行和上线后检查

清空待关口，按用户确认的范围逐步执行。每一步做完先读回实际结果，再把动作、目标及实际版本或发布记录写入 spec 变更记录，并按第 3 步第 5 小步写回。清单里有“合并（PR 或本地）”时，重做第 3 步第 3 小步，确认批准仍覆盖当前候选和生产影响，再按第 4 小步的对应路径执行。读回确认合并后处理写回，再做后面的动作：
- 发布和部署交给项目自己的方式，**遵循它自己的规则**（预演、备份、健康检查、回滚）。
- 任何一步失败，不要自行用破坏性手段补救（强推、删 tag、手动改服务器），停下来报告。
- 上线后检查：在 production 环境**只读**地检查（按 `post_check`；有测试浏览器时打开线上地址截图），并看一眼部署之后的错误日志有没有新增（项目验证 skill 里写了怎么看）；不提交表单、不写数据。`post_check` 里某一项在这个项目上做不到（比如页面上不显示版本号），用等价的只读检查代替（部署记录、`/healthz`、接口返回），在汇总里说明，并建议用户改 `post_check`。发现新错误时写进汇总；**严重**（出现新的 5xx、进程崩溃或反复重启、错误数明显高于部署前）的按“失败”停下报告，并在报告里给出回滚方式。

完成后：状态改为“已发布”，阶段清空，同步索引，按第 3 步第 5 小步写回最终状态，更新汇总：发布了什么版本、检查结果、回滚方式。用户回“跳过”时，变更记录写“不上生产”并清空阶段。已合并的停在“已合并”，按同一规则写回；尚未合并的停在“已验证”，结束状态只在当前需求分支提交。
