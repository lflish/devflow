# 关口和汇总

人看的东西只有两种：**关口简报**（需要用户回复才能往下走）和**汇总**（告诉用户发生了什么、有哪些事等他决定；L2/L3 或离开模式下不用等回复）。

## 关口一览

| 关口 | 类型 | 谁发起 | 放行条件 | 用户要做什么 |
|------|------|--------|----------|--------------|
| 评审消息 | 人 | dev-requirements | 用户回复 | 回答前提、方案、范围、问题（都带推荐） |
| **A 需求确认** | 人 | dev-requirements | 用户回复通过 | 确认要做 / 不做、场景、假设；L3 一批需求一次确认 |
| **B 方案验证** | 机器 | dev-design | 方案验证结论“通过” | L1：看汇总后回复；L2/L3 或离开模式：只看汇总 |
| **可提测** | 机器 | dev-build | 4 个条件全满足（见 dev-build） | 不参与 |
| **C 独立验证** | 机器 | dev-test | 验证结论“通过”或“通过，有备注” | L1：看汇总后回复；L2/L3 或离开模式：只看汇总 |
| **合并** | 机器 | dev-release | 结论覆盖要合并的提交 | L1（包括离开模式）：确认；L2/L3：不参与 |
| **上生产** | 人 | dev-release | 用户回复通过 | 确认发布和部署清单 |
| `c<n>` | 人 | 任何阶段 | 用户回复 | 所有可做的工作都被这个决定卡住时 |
| 停-n | 人 | 任何阶段 | 用户回复 | 需求走不通时选方案 |

## 发出需要回复的简报时

1. 状态行写 `待关口：<关口>`（评审、A、B、C、合并、上生产、c<n>、停-n），提交当前产物；metrics.md 记一行“问用户”。机器关口在 L1 下等回复时，**“阶段”不改**，回复处理完再按下面的表改。
2. 在终端给出简报，有页面时链接放在第二行，访问码单独写，不放进链接。
3. 按 away.md 的“什么时候发”判断要不要通知（离开模式下发；不在离开模式时，只在距离用户上一条消息超过 15 分钟时发）。
4. 等用户回复。**这一轮到此结束。**

L2/L3 或离开模式下，机器关口 B、C 放行后只更新汇总，不写“待关口”，直接进入下一阶段（L1 离开模式的合并仍要确认）。

## 汇总（每次机器关口放行、或有事等用户时）

借鉴 pstack 的 ketchup。终端里一份，同时更新需求文件夹 `pages/summary/` 的汇总页（同一个链接，见 preview.md）。

```markdown
## <需求名> · <刚发生了什么，比如“独立验证通过”>

**等你的事**：2 件（没有就写“没有，继续往下做”）
**页面**：<url>　访问码：<code>（<到期日期> 过期）

### 等你决定
c1. <标题>
    你原来定的：…　建议：…
    依据：<运行证据或文件:行号>　风险：…　改错的代价：…
    我的推荐：保持原样　（T6 因此暂停，其余照常）
d2. <标题>　已按 A 做：<…>　备选 B：<…>　依据：<…>　风险：低

### 做了什么
<截图在前>
- 评论可以在预览页旁边发表和删除，12 个场景都在浏览器里走通了（证据：verdict.md、evidence/R1.1.png…）
- 修了一个问题：连点两次“发表”会出现两条评论（证据：回归测试 comments_double_submit_once 的输出）
- 验证者：<模型>；结论绑定提交 <短 sha>

每一句“做到了”后面都附证据（文件、截图、命令输出）；没有证据的不能写成“做到了”。

### 接下来
- 我会继续做：发布阶段的合并
```

写法：
- 第一句只说有没有事等用户。
- “等你决定”每条写清：要用户做的决定、推荐、依据、风险。一条一个决定，用户只看这条就能决定。
- “做了什么”按用户能感受到的变化写，一句一件事；正文不写提交号、测试条数这类细节，证据放在句末括号里（汇总页上做成可点开的链接）。
- 每页最多列 7 个 `d`；超过说明拆得太细，合并同类项。
- 不编造没有的截图和数字。

## 关口简报的格式

### 关口 A（规模“小”时加上技术方案；L3 时每个需求一节）

```markdown
## 关口 A：需求确认 · <需求名>

**一句话**：<要做什么；选的做法；范围模式>
**效果页**：<url>　访问码：<code>（<到期日期> 过期）
**完成条件**：<可检验的一句话，比如“12 个场景在浏览器里全部通过，旧接口无调用方”>

**要做**：…（3–6 条要点）
**不做**：…
**推迟**：E2 …
**验收场景**：共 12 个，最重要的：R1.1 …；R2.3 …；R4.1 …

### 我做的假设（可改）
H1. …（依据：…）

### 还需要你回答（都有默认）
Q3. <问题>　默认 A：…　备选 B：…

### 其他
- 自主等级：L1（新项目默认）
- 新建了 .devflow.yml，请看一下命令对不对

回复 `all` 全部按默认；或 `H2 改为 …`、`Q3 B`、`R2 去掉`、`按 L2 跑`、`问 H1`、`重做 <原因>`。
```

### L1 下机器关口之后

就是汇总，末尾加一行：`回复 all 往下走；或 d2 B、c1 同意、问 <编号>、重做 <原因>。`

### 上生产

格式见 dev-release。

## 解析回复

| 回复 | 含义 |
|------|------|
| `all`、`通过`、`ok`、`可以`、`同意` | 全部按默认。**例外：上生产只认 `all` 或明确的动作编号（如 `只到 1`）** |
| `继续`、`接着做` | **不是**通过：把当前等待的简报重发一遍（见 dev-workflow 的“判断从哪里接着做”） |
| `d1 B`、`d1 改成 <…>` | 改这个口味型决定，其余按默认 |
| `c1 同意` / `c1 不同意` | 采纳或不采纳这条建议 |
| `Q3 B`、`Q3 <简答>` | 回答这个问题 |
| `H2 改为 <…>`、`H2 不对` | 修改或推翻这条假设（推翻时按反面处理，拿不准就当作一个问题重新列出） |
| `P1 不同意：<…>` | 前提不成立，按用户的说法重新梳理受影响的部分 |
| `E2 加入` / `E2 推迟` / `E2 不做` | 扩展候选的去向 |
| `选 B` | 产品做法选 B |
| `M2`、`M2 + M3 的配色` | 多方案对比页里选定的方案（可以组合）；回 `all` 就是选推荐的那个 |
| `R2 去掉`、`R2.3 改为 <…>` | 删除或修改需求、场景 |
| `按 L2 跑`、`按 L3 跑` | 改这个需求的自主等级 |
| `问 <编号>` 或任何提问 | 先回答，再重新给出简报（只列有变化的部分），不算通过 |
| `重做 <原因>` | 回到这个阶段的开头，按原因修改 |
| 多项用逗号或换行隔开 | 逐项处理，没提到的按默认 |
| 用自己的话描述 | 按意思处理；拿不准对应哪一条时，说明理解并重新给出简报 |
| 看不懂的回复 | 不要猜。说明哪部分没看懂，重新给出简报 |

L2/L3 下，用户对汇总里的 `d`/`c` 作出回复时同样按这张表处理，不需要先暂停别的工作。

## 有改动时

1. 修改受影响的产物（spec、design、tasks、代码），在 decisions.md 追加一行记结果。
2. 重跑受影响的部分：
   - 改了需求或场景 → 更新 spec 和效果页（同一链接的新版本），受影响的设计和任务重新过机器关口 B。
   - 改了方案 → 重跑 dev-design 的工程评审和方案验证。
   - 要改代码 → 在 tasks.md 加“返工”任务（状态“待办”，写明来源），状态改回“开发中”，阶段改为 dev-build，之后依次走开发 → 测试。已经合并的需求不再改回：新开一个需求处理。
3. 重新给出简报或汇总，只列有变化的部分。
4. 同一个关口最多来回 3 轮。第 3 轮后还没通过，建议回到上一个阶段重新梳理。

**“通过，但先改一下”**：用户的回复既放行关口、又要求改一处（比如关口 C 回 `all`，而汇总里 `d2` 的推荐就是“现在改”；或者回 `C 通过，d2 B`）时：先按上面的做法改（代码改动走返工任务，“来源”写“关口 C 已放行，先改 d2”），按 verification.md 规则 4 复验；复验通过就按用户已经给的放行继续往下走，不再为同一个关口问第二次；复验不通过，或者改动超出用户说的范围，再发简报。

机器关口同一个原因 3 轮不通过时：记 `c<n>`，状态行写 `待关口：c<n>`，发汇总，这一轮结束；用户回复后按上表处理。

## 回复处理完以后：状态、阶段、“重做”回到哪

| 待关口 | 通过后：状态 → 阶段 | “重做 <原因>” 回到 |
|--------|---------------------|--------------------|
| 评审 | 不变 → dev-requirements（接着写 spec） | dev-requirements 第 3 步 |
| A（标准规模） | 已确认 → dev-design | dev-requirements 第 3 步 |
| A（小规模） | 开发中 → dev-build | dev-requirements 第 3 步 |
| B（L1） | 开发中 → dev-build | dev-design 第 2 步 |
| C（L1） | 已验证 → dev-release | dev-build（加返工任务） |
| 合并（L1） | 不变 → dev-release 第 3 步第 4 小步（合并前重新检查结论） | dev-release 第 3 步 |
| 上生产 | 不变 → dev-release 第 5 步 | 不执行，停在已合并 |
| c<n> | 不变 → 被卡住的阶段（解除对应任务的“阻塞”） | 用户给出的新方向：改 spec 的回到 dev-requirements，改方案的回到 dev-design |
| 停-n | 不变 → 停下时的阶段 | dev-requirements 第 3 步 |

每次回复处理完：
1. decisions.md 追加处理结果。
2. 按上表改状态行，清空“待关口”，同步索引。
3. spec 的“变更记录”写一句：哪个关口放行、改了什么。
4. 提交。
5. **在同一轮里立刻读那个阶段的 SKILL.md 并执行**。

机器关口 B、C 在 L2/L3 或离开模式下放行时不写“待关口”，直接按上表“通过后”那一列改状态和阶段。

## 从 L1 升到 L2 的条件

都满足时，在汇总里提示一句“这个项目可以升到 L2 了”，由用户决定，不要自己改：
1. 这个项目已经用 L1 跑完 2–3 个需求；
2. 项目专属的 `verify-<项目名>` skill 已生成并跑通；
3. 机器验证拦下过真问题（有过“不通过”并修好）；
4. 反复出现的错误已经变成自动检查（lint、类型、测试）。
