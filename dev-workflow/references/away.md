# 离开模式和通知：让 AI 等你，而不是你等 AI

用户不用盯着会话。把任务交出去后，AI 一直做到**真正需要用户**的那一刻，然后通知用户、停下来等。

## 进入和退出

- **进入**：用户说了类似的话：“我要走了”“去睡了”“做完叫我”“跑到下一个关口”“不用等我”。在状态行“等级”后面加 `离开`（例如 `等级：L1 离开`）。L3 本身不等于离开模式。
- **退出**：用户说“我回来了”，或开始和你实时对话（不是回复关口）时去掉 `离开`。**回复关口不会退出离开模式**：用户回完 `all` 又离开，是常态。

### 进入时（用户还在的时候）先自检，一次说清

1. **通知**：按下面“通知”一节确认能发出去。发不出去（没有推送工具、也没配 webhook）就当场告诉用户：“这次没法通知你，回来后说‘继续’看进度。”
2. **权限**：如果当前会话里执行命令需要用户逐个确认，离开后会卡住。当场提醒一句：“离开期间要是有命令需要你确认，任务会停在那里；如果介意，可以先放开这些权限。”不要自己改用户的权限设置。

## 离开模式下怎么做

- 关口之间的规则不变（只有人能做的事只暂停那一项，其余照常推进）。
- **L1 的“机器关口后看一眼”改为只更新汇总、不停下**，攒到下一个必须由人处理的点一起看；用户回来后可以在汇总里改任何 `d`/`c`。**但 L1 的合并仍然停下**：写 `待关口：合并` 并通知。
- 必须由人处理的点：关口 A、L1 的合并、上生产、`c<n>` 卡住全部工作、停-n、对外动作失败。到了这些点：**先通知，再结束这一轮**。
- 需要等外部的事（CI、部署、长时间的测试）：用会阻塞等待的命令（例如 `gh pr checks --watch`），或在后台运行并等完成通知；不要每隔几秒问一次状态，也不要因为在等而结束这一轮。

## 隔离：worktree

**主仓库根**：`dirname "$(git rev-parse --path-format=absolute --git-common-dir)"`。在 worktree 里也用它找本机配置里的本项目（config.md），不要用 `git rev-parse --show-toplevel`（在 worktree 里会返回 worktree 自己的路径）。

- 默认：每个需求在自己的分支 `change/<短名>` 上，在主仓库目录里做。
- **刚开始一个需求、而且处在离开模式、L3 一批需求、或用户还在主目录里干别的**：给这个需求建一个 worktree，放在主仓库里一个不进 git 的目录（在工作目录内，写文件不会触发额外的权限确认）：
  ```bash
  ROOT=<主仓库根>
  grep -qx '.devflow-tmp/' "$ROOT/.git/info/exclude" || echo '.devflow-tmp/' >> "$ROOT/.git/info/exclude"
  git -C "$ROOT" worktree add "$ROOT/.devflow-tmp/worktrees/<短名>" -b change/<短名> <默认分支>
  ```
  项目的测试、lint、构建工具会扫描整个目录的，要让它们忽略 `.devflow-tmp/`（改它们的忽略配置，记一行到 decisions.md）。
- **做到一半才进入离开模式**：留在当前目录继续做，不迁移到 worktree。
- 在 worktree 里装依赖、跑服务时，端口和数据目录要和其他 worktree、正在运行的服务错开（用的端口记进本机配置本项目下）。
- 需求合并或搁置后：`git -C <主仓库根> worktree remove .devflow-tmp/worktrees/<短名>`。

**一批需求并行**：工具支持子 agent 时，可以每个需求派一个子 agent 在自己的 worktree 里做，但子 agent **只做到“可提测”**（它接不到用户回复，也可能没法再派验证者）；测试阶段的独立验证、所有关口、`c<n>`、通知都由主会话处理。不支持时按顺序做。

## 通知

本机配置 `notify`（config.md）决定怎么发。按顺序用第一个能用的：

1. **推送工具**：当前工具有推送通知能力时（Claude Code 的 PushNotification：终端弹桌面通知，连了 Remote Control 时也推到手机）用它。
2. **webhook**：`notify.webhook_env` 指向的环境变量里有地址时，按 `notify.payload` 的格式发：

   | payload | 请求体 |
   |---------|--------|
   | `slack` | `{"text": "<消息>"}` |
   | `feishu` | `{"msg_type": "text", "content": {"text": "<消息>"}}` |
   | `wecom` | `{"msgtype": "text", "text": {"content": "<消息>"}}` |
   | `ntfy` | 请求体就是消息纯文本（不是 JSON），地址形如 `https://ntfy.sh/<你的主题>` |
   | `raw` | `{"title": "<标题>", "text": "<消息>", "url": "<汇总页链接>"}` |

   ```bash
   curl -fsS -m 10 -X POST "$WEBHOOK" -H 'content-type: application/json' -d '<请求体>'   # ntfy 去掉 content-type，-d '<消息>'
   ```
   地址只放环境变量，不写进文件，也不打印。
3. 都没有 → 不通知（进入离开模式时已经告诉过用户）。

**什么时候发**：
- **离开模式下**：到了上面“必须由人处理的点”，以及整个需求（或一批需求）跑完。
- **不在离开模式**：只在需要用户回复、而且距离用户上一条消息已经超过 15 分钟时发（他很可能走开了）。评审消息和关口 A 在非离开模式下不发。
- **不发**：日常进度、机器关口顺利放行、用户刚刚还在回复。

**写法**：一行，200 字以内，不用格式。先说要用户做什么，再说是哪个需求，最后附汇总页链接（访问码不放进通知）：
```
需要你确认上线清单：review-comments（发布 1.4.5）。汇总页 https://…
关口 A 待确认：comments，3 个方案已出效果页 https://…
```

## 用户回来时

用户回复后，按 dev-workflow 的“判断从哪里接着做”续上（它会先看 worktree 里的需求）。说“继续”只会重发等待中的简报，不算通过。
