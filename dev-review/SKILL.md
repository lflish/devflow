# dev-review：评审

目标：**用一双新的眼睛找出写代码的人看不到的问题，能修的直接修，不能定的交给关口。**

## 开始

1. 先读 `../dev-workflow/SKILL.md` 的“每次开始时”并照做（包括读 `../dev-workflow/references/decisions.md`）。
2. 状态行“阶段”改为 `dev-review`。
3. **独立模式**：没有需求文件夹（用户只是说“评审一下这段代码”）时，范围按人说的；没有 spec 就在结果开头写“无需求文档，只按代码本身评审”，把一致性检查换成“代码意图是否合理”。独立模式下**不直接改代码**，只给出评审结果，按严重程度列出，每条带改法，问人要修哪些。不写 review.md，不交接。

**接着做**：已有本轮 review.md 时，从“交关口决定”和“已修复”之后还没处理的问题继续。

## 1. 确定范围

- 基准：当前分支和默认分支的分叉点，`git merge-base HEAD main`（默认分支不是 main 时用实际的）。
- 改动文件：`git diff --name-only <基准>...HEAD`，再加上未提交的改动（正常情况下应该没有）。
- 自动生成的文件、锁文件、截图不用评审内容。

## 2. 独立评审

派一个全新的子 agent，用 [references/reviewer-prompt.md](references/reviewer-prompt.md)，清单是 [references/checklist.md](references/checklist.md)。
没有子 agent 工具时，自己按清单逐项检查，并在报告里注明“评审由同一上下文完成”。

## 3. 处理每个问题

按问题的类别处理（详见 decisions.md 第五节）：

| 类别 | 处理 |
|------|------|
| 明确错误 | **直接修**。是缺陷的，先写能复现它的测试并确认失败，再修，再跑测试。每个修复单独提交，`fix:` 开头 |
| 取舍 | 按决策原则定。决定改就改；决定不改，写一行理由。记为口味型 `d<n>` |
| 需求问题 | 不改需求，记为挑战型 `c<n>` |
| 检查放松 | **不自动处理**，不管看起来多简单都记为挑战型 `c<n>`，写清放松了什么、看到的理由 |
| 评审者错了 | 不采纳，写一行理由 |

修复后，重新运行全部测试（包括浏览器测试），附上输出。修复改动较大（超过 5 个文件，或改了接口）时，对新的改动再评审一次，最多一次。

## 4. review.md

```markdown
# 评审：<需求名>

日期：YYYY-MM-DD　范围：<基准>..<HEAD>，N 个文件　评审方式：独立子 agent / 同一上下文

结论：通过 / 有待决问题（见关口 C）

| 统计 | 严重 | 一般 |
|------|------|------|
| 已修复 | | |
| 交关口决定 | | |
| 不采纳 | | |

## 已修复
- [严重] 文件:行号 问题 → 怎么修的（提交 abc123，回归测试 xxx）

## 交关口决定
- d4 [一般] …（默认：…）
- c2 [严重] 检查放松：… 看到的理由：…（默认：恢复原检查）

## 不采纳
- [一般] … 理由：…

## 测试复跑
命令和结果
```

提交 review.md 和修复，阶段改为 `dev-accept`，然后读 `../dev-accept/SKILL.md` 并执行。

## 规则

- 还有未修复的“严重”问题时，关口 C 的简报里必须写进“紧急”一栏。
- 评审意见要定位到文件和行号，给出可执行的改法；“建议优化”这种空话不算问题。
- 不确定的先运行或读代码确认，不要凭感觉下结论。
