# 生成项目专属的验证 skill：verify-<项目名>

借鉴 pstack 的 create-verification-skill。每个项目需要一份“怎样像用户一样操作这个应用、怎样证明它是对的”的说明，写给**下一个没见过这个项目的 agent**看（包括独立验证者）。生成一次，之后每次测试和验证都用它，不再临时摸索。

放在项目的 skill 目录：Claude Code 是 `.claude/skills/verify-<项目名>/`，Codex 等是 `.agents/skills/verify-<项目名>/`；项目已经用了其中一个就用那个。它进仓库，**只认环境名（local、staging），不写任何真实地址**，地址按 dev-workflow 的 config.md 读取。

## 1. 先查项目，不问用户

从代码里回答下面的问题，只有观察不到的才问用户（通常不需要）：

- **用户接触什么**：网页、命令行、桌面应用、API、库？有多个时选主要的，其余记下。
- **怎么启动**：项目自己的开发命令（package scripts、Makefile、README），端口、环境变量、种子数据、登录方式。
- **怎么操作**：已有的 Playwright/Cypress 测试、脚本、可以 curl 的接口；没有就用：网页 → CDP 浏览器（dev-test 的 browser.md），命令行 → PTY 或 tmux，服务 → HTTP。
- **能拿到什么证据**：截图、页面快照、终端输出、响应内容、日志、退出码、数据库状态。
- **能不能隔离**：两个实例能不能同时跑（端口、数据目录）。不能的话写进 skill：宁可拒绝，也不去操作别人正在用的实例。

项目本身启动不了的，先修好或准确报告，再生成。

## 2. 写 SKILL.md

```markdown
---
name: verify-<项目名>
description: 像用户一样操作 <项目名>（<网页/命令行/…>）并取得证据。测试、验收、独立验证 <项目名> 的功能时使用。
---

# verify-<项目名>

## 启动
<在 local 环境启动的确切命令；怎样算就绪（日志行、页面上的元素），就绪指能用，不只是进程在；从空数据开始需要的迁移和种子数据；怎么关掉>
共享环境（staging 等）不启动，只按 .devflow.yml 的地址和数据规则使用。

## 体检
<一条只读检查：服务在、版本对、端口是我们启动的、登录有效。任何异常时先跑这个>

## 操作
<真实的操作方法：选择器（ARIA 名称、data-testid）、命令、路径；连浏览器按 dev-test 的 browser.md>

## 日志
<应用日志、错误日志、访问日志在哪（文件路径、journalctl 命令、docker logs、云服务的日志命令）；怎么只看本次操作之后的部分（按时间或请求 ID 过滤）；哪些关键字代表出错。远程主机、生产服务器只写环境变量名或 ssh 别名，不写真实主机名和 IP（这个文件进仓库）>
共享环境和生产只读地看，不改日志配置。

## 证据
<要截什么、存哪（需求流程里存到需求文件夹的 evidence/）；证明标准：
走用户真正的路径，不调内部接口；记录操作和操作后的状态；有副作用的（写文件、写库、发消息）要另外读一遍确认；操作后日志里没有新的错误>

## 清理
<关掉本次启动的实例、删掉临时数据；只关自己启动的，不按进程名杀；不删证据>

## 帮助脚本
<如果附带脚本：可执行，并写出调用方式>
```

每一节都写**这个项目的真实内容**，不留占位符。

## 3. 功能清单

建 `verify-<项目名>/features/README.md`（索引，加上所有功能共用的前提和操作约定），再给 3–5 个主要功能各写一个文件。每个文件四节：

- **子功能**
- **怎么到达**（用户视角）
- **怎么操作和验证**（用上面的方法，写清看到什么算对）
- **注意事项**（种子数据缺什么前提、已知的坑）

缺前提时，验证要报告失败并把原因写进“注意事项”，**不要为了通过而简化验证路径**。

## 4. 交付前实际跑一遍

按它自己写的步骤完整跑一遍：启动 → 体检 → 操作一个功能 → 取证据 → 清理。清理后确认证据还在。哪一步不对就改，每次失败后也要跑清理，别留下进程和端口。没跑通过的 skill 只是草稿，不能交付。

提交 skill，在 decisions.md 记一行。之后每个需求的 dev-test 会检查本需求涉及的功能是否在清单里，没有就补上。
