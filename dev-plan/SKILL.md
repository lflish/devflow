# 任务拆分

将 docs/design.md 中的设计方案拆解为可执行的开发任务清单，产出 docs/tasks.md。

## 执行步骤

### 1. 读取设计文档

读取 docs/design.md，提取以下关键信息：

- 系统模块划分与职责
- 数据模型与接口定义
- 技术选型与架构约束
- 非功能性要求（性能、安全等）

同时读取 docs/requirements.md 的验收标准，确保任务覆盖全部需求。

### 2. 划分里程碑

按交付价值将工作划分为 2-4 个里程碑（Milestone），每个里程碑是一个可独立验证的阶段。典型划分：

- M1：基础骨架与核心数据流（项目初始化、核心模型、最小可运行闭环）
- M2：核心功能完整实现
- M3：辅助功能、异常处理、边界完善
- M4：集成测试、文档、部署准备

### 3. 拆分任务

在每个里程碑下拆分具体任务，遵循以下规则：

- **粒度**：每个任务半天到两天可完成。如果估计超过两天，继续拆成子任务
- **独立性**：每个任务完成后系统应保持可运行状态
- **顺序**：先拆能形成最小可运行闭环的任务，再拆扩展功能

每个任务必须包含以下字段：

| 字段 | 说明 |
|------|------|
| 编号 | T1, T2, T3… 顺序编号 |
| 标题 | 一句话描述做什么 |
| 状态 | 待办 / 进行中 / 完成 |
| 里程碑 | 所属里程碑编号 |
| 描述 | 具体要做什么，实现要点 |
| 涉及文件 | 需要新建或修改的文件/模块列表 |
| 依赖 | 前置任务编号，无依赖写"无" |
| 完成定义 | 怎样算做完——具体的验证方法（能跑什么命令、能看到什么结果） |

### 4. 标注关键路径与并行项

- 用依赖关系画出任务的先后顺序
- 标出**关键路径**：最长依赖链上的任务序列，决定项目最短完成时间
- 标出**可并行项**：无相互依赖的任务组，可以同时推进

### 5. 生成 docs/tasks.md

按以下格式输出：

```markdown
# 任务清单

> 基于 docs/design.md 拆分，共 N 个任务，M 个里程碑。

## 关键路径

T1 → T3 → T5 → T7（示例）

## 可并行项

- T2 与 T3 可并行
- T4、T5、T6 可并行（示例）

---

## M1: 里程碑名称

### T1: 任务标题
- **状态**: 待办
- **描述**: 具体做什么，实现要点
- **涉及文件**: `src/xxx.ts`, `src/yyy.ts`
- **依赖**: 无
- **完成定义**: 运行 `xxx` 命令能看到 yyy 结果

### T2: 任务标题
- **状态**: 待办
- **描述**: ...
- **涉及文件**: ...
- **依赖**: T1
- **完成定义**: ...

---

## M2: 里程碑名称

### T3: 任务标题
...
```

### 6. 自检

输出前逐项检查：

- [ ] 每个设计模块都有对应任务覆盖
- [ ] 每条验收标准都能追溯到至少一个任务
- [ ] 没有超过两天的大任务
- [ ] 依赖关系无循环
- [ ] 每个任务的完成定义是可执行、可验证的
- [ ] 关键路径已标出

检查不通过则修正后再输出。
