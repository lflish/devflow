一句话 第 2 版

需求 → 设计 → 开发 → 测试 → 发布。人只做两类事：定方向（需求确认）和放行不可逆的动作（上生产）。方案、验收、合并由机器关口放行：没写过这段代码的验证 agent 在真实环境里跑一遍，给出“通过”才往下走。人看的是事后汇总，不是逐个确认。

人做什么，机器做什么 新

只有人能做

  • 定方向：要做什么、为什么、做完怎样算对（关口 A）
  • 口味：任何实验都定不了的产品偏好
  • 难以回头的决定：数据模型和迁移、对外接口、新的基础设施或付费依赖
  • 放松检查：删测试、调阈值、加忽略规则
  • 不可逆或对外：上生产、删数据、强推、对外发消息

机器验证代替确认

  • 方案是否覆盖需求、前提是否成立（机器关口 B）
  • 代码是否满足每个验收场景（机器关口 C）
  • 能合并到主干（凭验证结论，不凭 CI 全绿）
  • “选哪个方案”中能用运行结果回答的：做原型跑一下

人什么时候看

  • 关口 A：每个需求一次（L3 时一批需求一次）
  • 汇总：机器关口每放行一次就更新，第一句说清有没有事等你
  • 暂停项：只暂停那一件事，其他照常推进
  • 上生产前：一次确认

机器验证：怎样才算可信 新

借鉴 pstack 的 autopilot / shipping / interrogate。机器关口放行的唯一依据是验证结论，不是 CI 全绿，也不是写代码的 agent 说“做完了”。

规则为什么
验证者没写过这段代码：每次派全新的子 agent写代码的人只会检查自己想做的东西
在真实环境里跑：重跑测试和 lint，并用测试浏览器把每个关键场景像用户一样走一遍CI 和单元测试证明不了“用户用起来是对的”
问题要有运行证据：每个问题附上命令、输出和应有的结果；跑不出来的不算听起来有道理的意见不拦路，减少误报
结论绑定提交：结论写明对应的 commit；之后代码再变，要重新验证（小改一个验证者，大改全套）验证过的必须就是要合并的
只有用户会遇到的问题才拦：功能错、检查没过、文档写错；其余记进后续不因吹毛求疵卡住流水线
放松检查必须交给人：验证者发现测试、阈值、超时被放松，一律暂停这一项想过关的人最想放松检查

结论的三种结果

通过

往下走，进汇总。

通过，有备注

往下走，备注进后续清单和汇总。

不通过

回到开发修复，修完重新验证。同一问题 3 轮不过才找你。

项目专属的验证 skill（借鉴 pstack create-verification-skill）

每个项目第一次进入测试阶段时，生成一个 verify-<项目名> skill，写清：怎么启动、怎么检查实例状态、怎么像用户一样操作（真实的选择器和命令）、证据存哪、怎么清理；再为 3–5 个主要功能各写一份“怎么操作、看到什么算对”。生成后必须实际跑通一个功能才算交付。之后每次验证都用它，不再临时摸索。

自主等级：你想参与多少 新

写在 .devflow.yml 的 autonomy，也可以在提需求时说“这个按 L3 跑”。

等级适用你参与的点
L1 跟着看刚开始用、新项目、高风险改动关口 A；机器关口 B、C 通过后再请你看一眼；合并和上生产前确认
L2 常规信任建立后的日常需求关口 A；机器关口自动放行，你看汇总；合并凭验证结论；上生产前确认
L3 批量一批互相独立的小需求、迁移、清理一次确认整批需求和完成条件；之后自动跑到合并；上生产前确认一次；第二天看汇总

所有等级都不变

  • 难以回头的决定、改你定下的需求、放松检查 → 只暂停这一项
  • 上生产、删数据、强推、对外发消息 → 永远要你确认

从 L1 升到 L2 的条件（来自 pstack）

  1. 这个项目已经用 L1 跑过 2–3 个需求
  2. 项目专属验证 skill 已生成并跑通
  3. 机器验证能拦下问题（有过“不通过”并修好）
  4. 反复出现的错误已经变成自动检查

汇总长什么样（借鉴 pstack ketchup）

  • 第一句：有没有事等你
  • 等你的事逐条列：要你做的决定、推荐、依据、风险
  • 做了什么：截图在前，一句话一件事
  • 同时更新同一个 vibeview 汇总页

环境和配置放在哪 第 3 版

按“全团队一样还是因人而异”“敏不敏感”分三处。仓库里只写环境名和变量名，不写真实地址；每个人的地址都在自己机器的本机配置里。

信息例子放哪进仓库
有哪些环境、怎么用（全团队一样）有 local / staging / production；各自的数据规则；验收在哪个环境做；部署命令项目 .devflow.yml，地址只写变量名进
每个人自己的环境和地址你的开发机地址、staging 地址、浏览器访问你这台机器用的 IP本机 ~/.config/devflow/config.yml，按仓库根目录分组不进
跨项目、和机器有关的测试浏览器的 CDP 地址、vibeview 开关同一个本机配置的顶层不进
密钥和账号测试账号密码、token环境变量（配置里只写变量名）绝不进
# 项目 .devflow.yml（进仓库）：定义有哪些环境，不写真实地址
environments:
  local:
    start: npm run dev
    url_env: DEVFLOW_LOCAL_URL            # 没提供时用 http://localhost:3000
    data: 可随意读写，可重置
  staging:
    url_env: STAGING_URL
    deploy: "使用 $deploy-view 部署到 staging"
    data: 共享环境：只能用 e2e- 开头的测试数据，用完清理
    account_env: [STAGING_TEST_USER, STAGING_TEST_PASS]
  production:
    url_env: PROD_URL
    data: 只读：只做上线后检查，不提交表单、不写数据
test:
  e2e_env: local        # 开发时跑浏览器测试
  verify_env: staging   # 机器关口 C 独立验证；没有 staging 就用 local

# 本机 ~/.config/devflow/config.yml（不进仓库）：只写你自己的
browser:
  cdp_url_env: DEVFLOW_BROWSER_CDP
  host: 192.168.1.20                      # 浏览器访问这台机器用的地址
preview:
  vibeview: auto
projects:
  /home/you/github/your-project:           # 键是仓库根目录
    environments:
      local:   { url: http://192.168.1.20:3000 }
      staging: { url: https://staging.internal.example.com }

地址怎么取

按顺序取第一个有值的：① 环境变量（url_env 指的那个）② 本机配置里这个项目下的 url ③ .devflow.yml 里的默认值（只允许 localhost 这类不含真实主机的值）。

每个阶段用哪个环境

阶段环境权限
开发（单元、集成测试）不需要，或本机临时数据库—
测试（脚本化 E2E、探索式检查）e2e_env，默认 local可以随意造数据
机器关口 C（独立验证）verify_env按该环境的 data 规则，共享环境只动测试数据
发布后检查production只读

第一次在这台机器上用这个项目

AI 读 .devflow.yml 知道需要哪些环境，能推出来的自己补（local 地址、browser.host），推不出来的（比如 staging 地址）一次性问你，答案写进本机配置这个项目下，之后不再问。这次提问列入“允许问人的例外”。项目专属的 verify-<项目名> skill 进仓库，但只认环境名，不写地址。

每个阶段的约定

1 需求dev-requirements人：评审消息（必要时）+ 关口 A
进入条件
有新想法或新需求；或 spec 状态是“草案”
做什么
  1. 定规模，建需求文件夹和本地分支（微小改动直接改）
  2. 先查代码和文档
  3. 需求评审：前提挑战、产品方案（含最小可行）、范围模式、缺口扫描；能用原型回答的问题先做原型
  4. 你 一条评审消息，全部带推荐（没有歧义时跳过）
  5. 写 spec：需求写成“系统必须…”，每条配场景；写明完成条件
  6. 子 agent 新人通读检查
  7. vibeview 效果页（有界面或流程时）
产物
spec.md、decisions.md、pages/prototype/
结束于
关口 A 你看：要做 / 不做、关键场景、假设、效果页 → “已确认”。L3 时一批需求一页确认
小规模
关口 A 里顺带列出技术方案要点，确认后直接进开发
不做的事
不问代码能查到的；不问实现方法；不悄悄扩大范围；关口前不写产品代码
2 设计dev-design机器关口 B
进入条件
关口 A 通过
做什么
  1. 选方案：能实验的做原型定，其余按原则选
  2. 技术方案：结构、接口、数据、状态、安全、需求覆盖
  3. 前置验证：设计依赖的前提实际跑一遍
  4. 测试计划：每个场景分到单元 / 集成 / 浏览器
  5. 拆任务：文件、接口、对应场景、测试断言、完成定义
  6. 子 agent 独立工程评审（最后跑）
产物
design.md、tasks.md、方案简报（进汇总页）
结束于
机器关口 B 通过条件：每条需求有着落、前置验证全过、工程评审没有未处理的错误 → “开发中”。难以回头的决定暂停这一项交给你，其余任务照常开始
小规模
跳过这个阶段
不做的事
不停下来问“用 A 还是 B”；不为以后可能用到加抽象；不写空话
3 开发dev-build可提测
进入条件
机器关口 B 通过；或验证不通过后回来返工
做什么
  1. 逐个任务：先写测试并确认失败 → 实现 → 跑测试 → 提交 → 记进度
  2. 遇到问题自己裁决并记录
  3. 全量单元、集成测试和 lint
  4. 子 agent 调用 dev-review：问题要有运行证据；明确错误先写回归测试再修
产物
代码和提交、tasks.md 进度、review.md
结束于
可提测 任务都完成或标“阻塞”；测试和 lint 全过；评审没有未处理的严重问题；没有未提交的改动 → 自动进入测试
你参与
0 次（除只有人能做的那几类事）
不做的事
不一次做多个任务；不重构范围外代码；不放松测试来过关；不推送到远程
4 测试dev-test机器关口 C
进入条件
可提测
做什么
  1. 按 e2e_env / verify_env 取环境地址；这台机器第一次用这个项目时，缺的地址一次性问你并记进本机配置
  2. 项目还没有验证 skill 时先生成并跑通
  3. 补齐场景对应的测试；每个浏览器场景一个 Playwright 测试，提交进仓库
  4. 浏览器 探索式检查，修复（先写回归测试）
  5. 子 agent浏览器 独立验证：没写代码的验证者重跑测试、在真实浏览器里走每个关键场景、审 diff，给出结论（绑定 commit）
  6. vibeview 更新汇总页：结论、截图、待你处理的事
产物
浏览器测试代码、test-report.md（含验证结论）、evidence/
结束于
机器关口 C 结论“通过”或“通过，有备注” → “已完成”。“不通过” → 回开发，修完重新验证
不做的事
不改测试迁就错误的实现；不用操作你个人浏览器的工具；浏览器测试没做不能算通过
5 发布dev-release合并人：上生产
进入条件
机器关口 C 通过；或你说“发布”“上线”
做什么
  1. CI（需要时）：和本地一样跑
  2. 推送、开 PR、等 CI；合并前检查结论还覆盖要合并的代码，不覆盖就重新验证
  3. 合并 L2 / L3 凭验证结论合并；L1 先请你确认
  4. 你 发布和上生产：一份清单一次确认
  5. 浏览器 上线后检查，结果进汇总
产物
合并记录、版本、上线记录
结束于
上线完成 → “已发布”；不上线 → 停在“已合并”
不做的事
CI 全绿不等于可以合并；失败时不强推、不删 tag、不手改服务器

贯穿所有阶段

skill做什么
dev-workflow总纲：状态行和续做；自主等级；共用规则（决定分类、原则、只有人能做的事、机器验证规则、汇总格式、配置、vibeview 页面）
dev-review通用评审：开发阶段调用；你单独说“评审一下这段代码”时只给结果、不改代码
复盘以后再加：把反复出现的问题变成自动检查（升到 L2 的第 4 个条件会用到）

状态：草案 → 已确认 → 开发中 → 测试中 → 已完成 → 已合并 → 已发布；任何时候可以“搁置”。

为什么是 5 个阶段

理论标准拆得很细，实践中把总是一起做的合并。ISO/IEC/IEEE 12207 的 14 个技术过程像 OSI 七层，团队日常走的 5 步像 TCP/IP 五层。

阶段ISO/IEC/IEEE 12207 技术过程团队里的叫法
需求业务或使命分析、干系人需求定义、系统/软件需求定义需求评审、PRD
设计架构定义、设计定义、系统分析技术评审、技术方案、拆任务
开发实现、（部分）集成编码、自测、代码评审
测试集成、验证、确认提测、QA、验收
发布交付上线
不在单个需求内运行、维护、退役运维

需要你拍板（6 个，都有默认）

回 all 全部按默认；或 d5 B 这样改某一条。

d1. 开发阶段的 skill 叫什么

默认 A：dev-build

B：沿用 dev-implement

d2. 合并掉的旧 skill（dev-plan、dev-implement、dev-accept、dev-cicd）

默认 A：直接删除，git 历史里还在

B：保留一个版本做转发

d3. 验证通过后代码又改了

默认 A：小改（修复、变基）派一个验证者复验；新功能或大改动重跑全套验证

B：任何改动都重跑全套

d4. 复盘

默认 A：先不做，跑过几个需求再加

B：现在就加 dev-retro

d5. 默认自主等级 新

默认 A：新项目从 L1 开始，满足 4 个条件后我提示你升到 L2

B：直接用 L2

d6. 验证者用什么模型 新

pstack 让验证者用和写代码不同的模型家族，盲区更少。你本机装了 Codex。

默认 A：先用同一个模型的全新子 agent，简单可靠

B：装了 Codex 时，再加一个 Codex 验证者做第二意见（会消耗 Codex 额度）
