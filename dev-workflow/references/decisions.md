# 决定怎么做：分类、原则、只有人能做的事、记录

阶段之间，AI 会遇到很多需要做决定的地方：方案选哪个、spec 没写到的细节、计划里的漏洞、评审意见要不要采纳……
**这些都由 AI 自己定，不停下来等人。** 定错了，用户在汇总里能看到、能撤回；停下来等人，会耽误用户一整天。

## 一、别一轮轮试错：让运行结果和对比来回答

不要和用户一轮轮地“改一下 → 不满意 → 再改一下”，也不要自己一个思路接一个思路地瞎试。先造一个能自动试、自动评估的小工具，再让结果说话。

### 1. 能用运行结果回答的，不问人

想问“选哪个方案”“这样做行不行”之前，先判断：答案能不能通过运行观察到？行为、时间、布局、输出、性能、两个方案哪个更快——这些都能。能 → 按下面第 3 条做实验；不能（纯粹的产品偏好、业务取舍）→ 按第 2 条给出多个方案，或按第二节分类处理。

### 2. 口味类的决定：一次给出多个方案，让用户一次选定

界面布局、视觉风格、文案语气、交互方式这类“看了才知道喜不喜欢”、**而且选错了返工很大**的事，不要先做一个再一轮轮改（选错了也很容易改的小事，直接按推荐做，记口味型 `d`）。多方案只在**需求阶段的效果页**里出；关口 A 之后遇到的口味选择一律按推荐做，记 `d<n>`，不再做多方案页、不停下来等：
- 一次做 **2–4 个真正不同的方案**（本机配置 `variants` 可改上限），放进**同一个**对比页，用顶部按钮或数字键切换，每个方案标编号 `M1`、`M2`…和一句话特点；
- 写明推荐哪个、为什么；
- 在关口 A（或汇总里）请用户一次选定：回 `M2`，或 `M2 + M3 的配色` 这样组合。
- 做法见 preview.md 的“多方案对比页”。

### 3. 不明显的问题：假设 → 实验 → 数据

性能问题、偶发 bug、“为什么不工作”这类原因不明显的问题，不要一个修法接一个修法地试：
1. **先做验证工具**：一个能反复运行、给出数字或明确对错的脚本（基准测试、复现脚本、对比截图），在改动之前跑一遍，留下“改之前”的数据。脚本放进项目（测试或 `scripts/`）就能重复使用；一次性的放 `.devflow-tmp/`。
2. **列出 2–4 个假设**：每个假设写清“如果是它，那么某个实验会看到什么”。
3. **每个假设一个实验**，用第 1 步的工具跑出数据；能并行的并行（子 agent 或后台）。
4. **按数据决定**改哪里；改完再用同一个工具跑一遍，和“改之前”比较。
5. 数字要先弄清楚它测的是什么：瓶颈在哪、有没有测到别的东西、多跑几次是否稳定，然后才相信它。

实验的假设、数据和结论记进 decisions.md（一行一个结论，依据写“实验”，附数据文件路径），并在 metrics.md 记一次“原型实验”。要当作证据引用的数据和截图放进需求文件夹的 `evidence/`（`.devflow-tmp/` 不提交，删了就没了）。

## 二、每个决定先分类

| 类型 | 是什么 | 处理 |
|------|--------|------|
| **机械型** | 只有一个合理答案：文件放哪、命名、用项目里已有的库、按项目惯例写 | 直接定。重要的记一行，琐碎的不用记 |
| **口味型** `d<n>` | 两个以上方案都合理，取舍不同；范围在边界上；独立评审的意见和你不同、但有道理 | 先按推荐定下来**继续做**。记一行，写进汇总，用户可以改 |
| **只有人能做** `c<n>` | 见第四节的清单 | **只暂停这一项**：按用户原来定的继续做其余部分；记一行，写进汇总，等用户决定 |

拿不准是口味型还是“只有人能做”时，按“只有人能做”处理。

## 三、决策原则（自己做决定时按这个顺序）

1. **以 spec 为准**：spec 写了的照做；计划是对 spec 的展开；两者都没写的，才靠下面几条。
2. **复用已有**：项目里已有的函数、库、模式，优先用，不重复造。
3. **直白优先**：选一个新人一眼能看懂的写法。十行直白的代码好过两百行的抽象。
4. **影响范围内补全**：**当前任务或当前修复本来就要改的文件**里，和这次改动直接相关的明显缺口（漏了错误处理、漏了边界情况），顺手补上，不引入新依赖。这是对“最小改动”的唯一放宽：不为补全而去改其他文件，也不做重构。
5. **不扩大范围**：超出第 4 条的改进，记进 `tasks.md` 末尾的“后续”清单，不做。
6. **倾向行动**：有顾虑就记下来，继续往前走，不卡住。

设计阶段第 2、3 条优先；开发阶段第 3、4 条优先。

## 四、只有人能做的事

| 类别 | 例子 | 怎么处理 |
|------|------|----------|
| **定方向** | 要做什么、为什么、做完怎样算对 | 关口 A |
| **改用户定下的东西** | 改需求、范围、验收场景 | 记 `c<n>`，只暂停受影响的部分 |
| **口味** | 任何实验都定不了的产品偏好 | 能做成可对比的方案的，按第一节第 2 条一次给出多个方案让用户选；其余先按推荐做（口味型 `d`），返工很大的记 `c<n>` |
| **难以回头的决定** | 迁移或改动**已有**数据；破坏对外接口的兼容性；新的基础设施或付费依赖。（新增表、新增字段、新增接口不算，按机械型或口味型处理） | 记 `c<n>`，只暂停依赖它的任务 |
| **放松检查** | 删测试、跳过测试、放宽断言、调大超时、加忽略规则 | 记 `c<n>`，保持原检查 |
| **不可逆或对外** | 上生产（包括“合并就会自动部署生产”的合并）、删数据、改生产数据库、`git push --force`、删分支、对外发消息、调用会产生费用的外部服务 | 不做；发布阶段集中一次确认 |
| **安全敏感** | 处理真实密钥或凭据、改权限或认证配置、把开发服务临时暴露到公网（为了让云浏览器能打开） | 不做；写进汇总等用户决定 |
| **需求根本走不通** | 核心需求自相矛盾、依赖的外部服务不存在 | 唯一需要**整体停下**的情况：按 [questions.md](questions.md) 问，并按 [preview.md](preview.md) 生成对比页，状态行写 `待关口：停-<n>` |

“只暂停这一项”的意思：在 tasks.md 把受影响的任务标为“阻塞”并写明等哪个 `c`，其余任务照常做完；机器关口在结论里列出这些未决项。所有任务都被它卡住时，才变成整体等待。

**以下都不是停下来的理由**：“要不要继续”、汇报进度、“我做了个决定想确认一下”、发现小问题、计划有小漏洞、测试失败、评审有意见、验证不通过。这些都用分类、记录和返工处理。

### 这些动作不需要确认，直接做

- 用 dview 上传页面（默认带访问码保护），读取 `DVIEW_TOKEN`
- 连接配置好的测试浏览器（CDP 或云浏览器；云浏览器只用于公网地址，项目没写 `cloud_browser: forbidden`），打开 `e2e_env`、`verify_env` 环境；按该环境的数据规则造和清理测试数据
- 从环境变量读测试账号（不打印出来）
- 建本地分支、本地提交、建 git worktree
- 推送 `change/*` 分支、开 PR（会通知仓库的代码负责人，这是预期的）
- 按下面“写回默认分支”的做法，提交**只改 `docs_dir` 下文件**的更新：合并后写回状态和数据、L3 批量开始前登记这一批需求、记录“合并后发现问题”
- 按 `.devflow.yml` 里某个**非生产**环境配置的 `deploy` 命令部署到该环境（团队写了这条命令，就是同意 AI 用它）
- 安装开发和测试依赖（`npm i -D`、`pip install -r requirements-dev.txt` 等），下载测试用浏览器（`npx playwright install chromium`）
- 启动、停止本地开发服务
- 在本机建立到已配置主机的 SSH 隧道（`browser.ssh_host`）
- 派子 agent，或按 verification.md 调用本机配置的其他模型做验证
- 按 away.md 给用户发通知（只在有事要用户处理时）
- 在仓库外建 worktree（away.md），在里面装依赖、启动服务

### 写回默认分支

需求合并后，状态、变更记录、索引、metrics.md 要回到默认分支上。不要切换用户主目录的分支（他可能正在那里干活）：
1. 有远程仓库：
   ```bash
   ROOT=<主仓库根>; git -C "$ROOT" fetch -q origin <默认分支>
   git -C "$ROOT" worktree add --detach "$ROOT/.devflow-tmp/writeback" origin/<默认分支>
   # 在 writeback 里只改 docs_dir 下的文件，提交
   git -C "$ROOT/.devflow-tmp/writeback" push origin HEAD:<默认分支>   # 分支受保护推不上去时，改为推一个分支并开只含这些文件的小 PR
   git -C "$ROOT" worktree remove --force "$ROOT/.devflow-tmp/writeback"
   ```
2. 没有远程仓库：用户主目录正好在默认分支上、而且没有未提交的改动时，直接在那里提交；否则先不写回，在汇总里列一条“待写回”，下次满足条件时补上。

### 允许问人的例外

1. 开头找不到当前需求：有多个未完成的需求，看不出用户指的是哪个。
2. 需求评审消息（dev-requirements）：一轮；用户不同意前提、且影响大时，最多再追问一轮，只问受影响的部分。
3. 关口 A；L1 下机器关口之后的汇总；发布阶段的对外动作确认。
4. 用到某个环境、却取不到地址又推不出来时（不限第一次，见 config.md）：一次性问完所有缺的地址，写进本机配置。
5. 对外动作执行中失败（CI 同一问题失败 3 次、部署失败）：停下报告，不自行用破坏性手段补救。

## 五、裁决记录

每个需求一份 `decisions.md`（在需求文件夹里），**只追加，不修改旧行**：定错了就加一行新的写明推翻哪一行。每个记录在案的决定一行，**做完决定立刻记**：

```markdown
| # | 阶段 | 决定 | 类型 | 依据 | 理由 | 放弃的选项 | 定错的代价 | 处理结果 |
|---|------|------|------|------|------|------------|------------|----------|
| 1 | 设计 | 评论存 SQLite 新表 | 机械 | 原则2 | 项目已用 SQLite | 存 JSON 文件 | 低 | — |
| 2 | 设计 | 用原型比较了两种分页方式，选游标分页 | 机械 | 运行结果 | 1 万条时快 6 倍（.devflow-tmp/page-bench.txt） | 偏移分页 | 低 | — |
| d1 | 设计 | 评论按页面版本隔离 | 口味 | 原则1 | spec 要求评论对应版本 | 跨版本共享 | 中：要改展示逻辑 | 汇总 #2 用户采纳 |
| c1 | 开发 | 建议去掉“匿名评论” | 只有人能做 | — | 和访问码权限冲突 | 保留 | 高 | 等用户；T6 阻塞 |
```

- 编号：机械型用数字，口味型 `d1, d2…`，只有人能做的 `c1, c2…`，在整个需求里连续编号。
- “处理结果”列：用户回复后在**新的一行**写结果（例如“d1：用户改为 B”），不改旧行。
- 汇总和关口简报从这张表汇总；换会话时也从这里续上。

## 六、独立评审意见怎么处理

设计评审、代码评审、机器验证都由**没看过过程**的子 agent 来做（同一个上下文自己审自己，盲区是一样的）。它的意见：

- 明确的错误、有运行证据、有清楚的改法 → 机械型，直接改。
- 有道理但可改可不改 → 口味型 `d<n>`。
- 要求改需求或范围，或涉及第四节的事 → `c<n>`。
- 没有运行证据、只是“听起来有问题” → 先自己跑一下确认；确认不了的不采纳，记一行理由。
- 你认为它错了 → 可以不采纳，但要在 `decisions.md` 里写一行理由。
