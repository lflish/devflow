# dev-workflow —— 软件开发全流程总纲

## 阶段总览

| # | 阶段 | Skill | 核心产物 | 过关标准 |
|---|------|-------|---------|---------|
| 1 | 需求 | dev-requirements | `docs/requirements.md` | 需求文档已写且用户已确认，无未决问题 |
| 2 | 设计 | dev-design | `docs/design.md` | 设计文档已写，关键技术选型已决策，前置验证项全部通过 |
| 3 | 任务拆分 | dev-plan | `docs/tasks.md` | 任务列表已拆至可直接编码的粒度，每条有明确完成定义 |
| 4 | 实现 | dev-implement | 代码 + 提交 | 所有任务标记完成，代码可编译/运行 |
| 5 | 测试 | dev-test | 测试用例 + 测试报告 | 核心场景覆盖，全部通过 |
| 6 | 评审 | dev-review | `docs/review-<date>.md` | 评审意见已逐条处理，无阻塞项 |
| 7 | CI/CD | dev-cicd | CI 配置 + 部署脚本 | 流水线绿灯，可部署到目标环境 |

## 使用方式

### 1. 判断当前阶段

进入项目目录后，按以下顺序检查产物文件，找到第一个不存在或内容不完整的文件，即为当前应进入的阶段：

1. 检查 `docs/requirements.md` 是否存在且内容完整（无"待拍板"未决项）
2. 检查 `docs/design.md` 是否存在且前置验证项全部标记通过
3. 检查 `docs/tasks.md` 是否存在且任务已拆分
4. 检查代码实现进度（对照 tasks.md 中的任务列表）
5. 检查测试是否编写并通过
6. 检查是否已做评审
7. 检查 CI/CD 是否配置

然后告诉用户："当前项目处于 **XX阶段**，下一步应该……"，并指引调用对应的 skill。

### 2. 进入某个阶段

每个阶段开始前，**必须先读取上一阶段的产物文件**，确保对齐上下文。例如进入设计阶段前，先读 `docs/requirements.md`。

### 3. 阶段间的产物约定

所有文档产物统一放在项目根目录的 `docs/` 下：

- `docs/requirements.md` —— 需求文档
- `docs/design.md` —— 技术设计文档
- `docs/tasks.md` —— 任务拆分清单
- `docs/review-YYYY-MM-DD.md` —— 评审记录（按日期命名，可多份）

如果 `docs/` 目录不存在，在第一个阶段开始时创建。

### 4. 过关原则

- **不跳阶段**：每个阶段必须产出对应文件且内容达标，才能进入下一阶段。
- **产物驱动**：不是"聊完了"就算过关，而是产物文件落地且用户确认。
- **未决不前进**：需求文档中有"待拍板"项时，不进入设计；设计文档中有"前置验证项"未通过时，不进入任务拆分。

### 5. 快速通道

对于小改动（bug 修复、小功能补丁、配置调整等），不需要走全流程。快速通道只过三个阶段：

1. **实现**（dev-implement）—— 直接编码
2. **测试**（dev-test）—— 验证改动
3. **评审**（dev-review）—— 简要评审

判断是否适用快速通道的标准：
- 改动范围小于 3 个文件
- 不涉及架构变更或新依赖引入
- 不改变已有接口契约

如果不确定，走完整流程。

### 6. 阶段 Skill 速查

当需要进入某个阶段时，直接调用对应 skill：

- 需求讨论 → `/dev-requirements`
- 技术设计 → `/dev-design`
- 任务拆分 → `/dev-plan`
- 编码实现 → `/dev-implement`
- 测试验证 → `/dev-test`
- 代码评审 → `/dev-review`
- CI/CD 配置 → `/dev-cicd`
