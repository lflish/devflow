# spec.md 模板

规模“小”时可以只写：背景与目标、完成条件、范围、需求与场景、假设、变更记录。

```markdown
# <需求名>

状态：草案　阶段：dev-requirements　待关口：—　等级：L1　规模：标准　创建：YYYY-MM-DD　更新：YYYY-MM-DD

## 背景与目标

为什么要做：现在的问题是什么，现在怎么绕过去的。（两三句）
做完的样子：怎么判断做对了。（一两句，能量化就量化）

## 完成条件

一句可检验的话，机器关口 C 按它判断。例如：R1–R4 的 12 个场景在浏览器里全部通过；旧接口 `/api/old-comments` 没有调用方并已删除。

## 前提

需求评审时和人确认过的前提（见 product-review.md）：

- P1 …（已确认）

## 做法与范围

做法：<选了哪个产品层面的方案，一句话；放弃的方案和原因一句话>
范围模式：选择性扩展

要做：
- …

不做：
- …（写容易被误以为要做的，附理由）

推迟到以后：
- …（评审时选了“推迟”的扩展）

已有可复用：
- <模块或功能>：用来 …

理想状态对照（标准规模）：现状 … → 本次 … → 一年后 …

## 需求与验收场景

### R1 <需求名>

系统必须 <一个外部能观察到的行为>。

- **R1.1 <场景名，说清是什么情况>**
  假如 <前提>
  当 <操作>
  那么 <结果>
- **R1.2 <出错 / 空 / 无权限的情况>**
  假如 …
  当 …
  那么 …

### R2 …

## 非功能要求

只写真有要求的，并且量化。没有就删掉这一节。

- 性能：…
- 安全：…

## 假设

AI 在没有明确说法时做的决定，关口 A 可以改。

| # | 假设 | 依据 |
|---|------|------|
| H1 | 评论只支持纯文本 | 项目里所有用户输入都按纯文本处理 |

## 问答记录

- YYYY-MM-DD Q：… → A：…

## 效果页

<vibeview 链接>（访问码另给，不写在这里）

## 变更记录

- YYYY-MM-DD 关口 A 通过；Q2 改为 B，H3 推翻。
```

## 写法要点

- 需求编号 R1、R2；场景编号 R1.1、R1.2。后面的任务、测试、验收都按这个编号对应，**编号定了就不要改**，删掉的写“（已取消）”。
- 一条需求只说一个行为；要用“并且”连起三件事的，拆成三条。
- 场景名要说明情况，比如“R2.3 访问码过期后打开链接”，不要写成“场景 3”。
- 写完问自己一句：**哪个情况坏了我最不能接受？** 确保有一个场景点名覆盖它。
