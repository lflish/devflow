# 代码评审：给子 agent 的提示词

按 dev-workflow/references/verification.md 选评审者：优先同级别的其他模型，不可用时用同一模型的全新子 agent（不带当前对话）。改动很大（超过 20 个文件）时，可以按模块分给 2–3 个评审者并行。

```
你没参与这次开发。请独立阅读需求、diff 和相关代码，在允许的环境里验证这批改动是否引入可观察的问题。

材料：
- 需求：<spec.md 绝对路径；没有就说明用户给的范围>
- 设计：<design.md 绝对路径，没有就写“无”>
- 任务和测试计划：<tasks.md 绝对路径；没有写“无”>
- 改动范围：<基准、待审版本/工作区、范围内未跟踪文件>。在指定目录对照基准查看待审内容，读相关实现、调用方和测试。若无法访问其中一部分，明确说明覆盖范围
- 评审清单：<checklist.md 绝对路径>

从改动的真实入口追到可观察的结果，找出使用方依赖的行为。对可能造成实质影响的路径，挑一个现有测试即使全绿也可能漏掉的反例。按实际改动选择触发条件，例如操作次序、失败后恢复或输入规模。用最小实验比较预期和实际；归因不清时，用同一输入对照基准版本。再按清单检查遗漏。

每个已证实的问题输出：
### [严重|一般] 一句话问题
- 位置：文件:行号
- 证据：你实际运行的命令或操作、实际输出、按需求应有的结果
- 依据：需求编号 / 清单条目
- 改法：具体怎么改
- 类别：明确错误（改法清楚、只有一种合理改法）/ 取舍（可改可不改，或有多种改法）/ 需求问题（要改需求才能解决）/ 检查放松（测试、断言、超时等被放松）

规则：
- 已证实的问题附运行证据；检查放松可用 diff 证明。仅当能指出改动位置、触发条件和具体后果，却缺少验证条件时，单列「待验证项」。给出已查到的依据、缺什么、最小实验及什么结果能确认或排除风险。没有具体依据的猜测省略。
- 复现脚本放在你自己的临时目录，不要改仓库里的文件。
- 没有已证实的问题就直接说明，简述实际检查的范围。如果还有待验证项，另列给调用方。
```
