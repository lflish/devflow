流程总览

上面一行是你，下面一行是 AI。人只做两类事：定方向（关口 A）和放行不可逆的动作（上生产）。其余关口由机器验证放行，你看事后汇总。

阶段详情

自主等级：你想参与多少

等级适用你参与的点
L1 跟着看（新项目默认）刚开始用、新项目、高风险改动关口 A；机器关口 B、C 通过后看一眼；合并前确认；上生产前确认
L2 常规信任建立后的日常需求关口 A；机器关口自动放行，你看汇总；合并凭验证结论；上生产前确认
L3 批量一批互相独立的小需求一批需求一次确认关口 A；自动跑到合并；整批一份上生产清单

所有等级都一样：难以回头的决定、改你定下的需求、放松检查 → 只暂停那一项；上生产、删数据、强推、对外发消息 → 永远要你确认。L1 升 L2 要满足 4 个条件：跑过 2–3 个需求、项目验证 skill 跑通、机器验证拦下过真问题、反复的错误已变成自动检查。

一个需求走一遍（L2）

以“给预览页加评论”为例，标准规模，等级 L2。橙色是你，蓝色是 AI，绿色是机器关口。

2 次需要你回复
3 个机器关口替你验证
1 个持续更新的汇总页
0 次开发中被打断

让 AI 等你，而不是你等 AI

说“我要走了”“做完叫我”，进入离开模式：AI 一直做到真正需要你的那一步，通知你，再停下。

做到哪一步才叫你

  • 关口 A：确认需求
  • L1 的合并、上生产
  • 某个只有你能定的事卡住了全部工作
  • 需求走不通、对外动作失败
  • 整个需求跑完

离开模式下，L1 的机器关口也不停，只更新汇总；回来后你可以改任何决定。

怎么通知你

  • Claude Code 推送：终端弹窗，连了 Remote Control 也推到手机
  • webhook：飞书、企业微信、Slack、ntfy
  • 只在有事要你处理时发；不在离开模式时，只有你超过 15 分钟没说话才发
  • 通知里带汇总页链接，不带访问码

不打扰你手上的事

  • 需求在 .devflow-tmp/worktrees/<短名> 里做，不切换你主目录的分支
  • 一批需求可以并行，子 agent 只做到可提测，关口和通知由主会话处理
  • 进入时先检查通知能不能发出去、会不会被权限确认卡住

用数据说话：devflow 到底有没有用

每个需求记一份 metrics.md

  • 每个阶段的开始和结束
  • 问了你几次、你多久回复
  • 机器关口跑了几轮、验证者是谁
  • 拦下几个问题、返工几次、做了几次实验
  • 合并后又发现几个问题（修 bug 时用 git 查出是哪个需求引入的）

统计页

说“统计一下 devflow 的效果”，汇总所有需求：耗时、打扰你的次数、等你的时间、机器关口轮次，以及最关键的一项：

合并后发现的问题 ÷ 验证拦下的问题，越低说明机器验证越靠谱。

为什么要记

规则越加越多，不测就不知道哪些真有用。有了数据，才能删掉没用的规则，或者做“用 / 不用 devflow”的对照实验。

机器验证：怎样才算可信

六条规则

  1. 验证者没写过这段代码
  2. 在真实环境里跑：测试 + 测试浏览器走每个场景
  3. 每个问题要有运行证据，跑不出来不算
  4. 结论绑定代码指纹，代码变了就复验（只改文档不复验）
  5. 只拦用户会遇到的问题
  6. 放松检查一律交给你

验证者用谁

  1. 按本机配置 verify.models 顺序探测（默认 codex → claude → same），60 秒不通就换下一个
  2. 跳过当前写代码的那个模型
  3. 都不行：同一模型的全新子 agent
  4. 连子 agent 都没有：同一上下文验证，不能自动放行

结论里写明用了谁、为什么。

项目验证 skill

每个项目第一次测试时生成 verify-<项目名>：怎么启动、怎么体检、怎么像用户一样操作、证据存哪、怎么清理，加上主要功能清单。必须实际跑通才算交付；只认环境名，不写地址。

共用规则（dev-workflow/references）

别一轮轮试错

  • “行不行”“哪个快”能跑出答案的，跑一下，不问人
  • 看了才知道喜不喜欢、选错返工大的：效果页里一次出 2–4 个方案，你回 M2 一次选定
  • 原因不明显的问题：先做验证脚本留下“改之前”的数据，再“假设 → 实验 → 数据”

决定分三类

  • 机械型 直接定
  • 口味型 d 按推荐做，进汇总，你可以改
  • 只有人能做 c 只暂停这一项，其余照常

只有人能做的事

  • 定方向、改你定下的需求
  • 实验定不了的产品偏好
  • 迁移已有数据、破坏对外兼容、新基础设施或付费依赖
  • 放松检查
  • 上生产、删数据、强推、对外发消息、安全敏感

决策原则（按顺序）

  1. 以 spec 为准
  2. 复用已有
  3. 直白优先
  4. 本来要改的文件里补全缺口
  5. 不扩大范围
  6. 倾向行动

不需要确认，直接做

  • 上传 vibeview、连测试浏览器
  • 本地分支、提交、worktree；推送 change/*、开 PR
  • 装测试依赖、启停本地服务
  • 按配置部署到非生产环境
  • 合并后只改需求文档的状态提交

回复怎么写

  • all 全部按默认
  • d2 B　c1 同意　Q3 B　H2 改为 …
  • 按 L2 跑　问 d3　重做 <原因>
  • “继续”不算通过；上生产只认 all 或动作编号

待关口（在等你）

评审 / A / B / C / 合并 / 上生产 / c<n> / 停-n。你说“继续”时，AI 把等待中的简报重发给你，不会当成通过。

配置放在哪

# 项目 .devflow.yml（进仓库）
autonomy / commands / rules / release
environments: 只写环境名、变量名、数据规则
test: e2e_env / verify_env

# 本机 ~/.config/devflow/config.yml
browser / preview / verify.models
projects:
  <仓库根目录>:
    environments: 你自己的真实地址

仓库里不写真实地址；密钥只放环境变量。
